## C-10. 장치 실패 처리 (2026-11-06, 사용자 결정)

- 환경 점검 카메라 항목은 영상뿐 아니라 녹화 시작 가능 여부까지 본다. 녹화할 수 없는 브라우저는 점검을 통과하지 못한다.

## C-14. 남은 논의사항 정리 (2026-11-09, 사용자 결정)

- 문서마다 남아 있던 논의사항 70개 중 32개는 코드·실측으로 확인해 닫았다(TTS 는 CPU, GPU 는 llm-rt·stt, embed 1.6~1.9GB 등). 나머지는 아래 결정대로 처리했다.

- 영향: 점수가 나오는 방식이 바뀐다(판정 규칙 변경). 온도 0 이 LLM 서버를 다시 띄운 뒤에도 같은 점수를 내는지는 재지 않았다. 개인용 문서 반영.
- 남은 흔들림(2026-11-09 사용자 결정: 그대로 둠): LLM 서버가 동시에 들어온 요청을 묶어 계산하므로, 진행 중 면접과 채점이 겹치면 온도 0 이어도 점수가 조금 달라진다(실측 65.40 ↔ 66.15, 다른 일이 없을 때는 65.40 고정). 채점 시간을 나누거나 채점 전용 모델로 옮기지 않는다.

## C-15. AI 공고 초안을 LangGraph 그래프로 (2026-11-10, 사용자 결정)

- 원래: 공고 초안(T9, S-R02)은 LLM 1번 호출(실패하면 1번 더) 뒤 그대로 저장하고, 차별 표현은 알리기만 했다. LangGraph 그래프는 질문 만들기·면접 진행 2개였다.
- 바꾼 것 (`services/posting_draft.py`, 사용자 요청 ①~④ 모두):
  ① **참고 공고 찾기(retrieve)**: 같은 직무의 게시·마감 공고 최근 2건을 프롬프트에 '용어·문체만 참고, 그대로 옮기지 말 것'으로 넣는다. 직무 코드로 정확히 찾으므로 벡터 검색·DB 변경 없이 DB 조회로 한다.
  ② **칸별 검사·다시 쓰기(check → rewrite)**: 문제가 있는 칸만 다시 쓴다(칸마다 `REWRITE_LIMIT` 1번). 다시 쓴 글이 형식에 안 맞으면 버리고 앞의 글을 둔다.
  ③ 검사 항목: 차별로 보일 수 있는 표현(규칙 사전, 화면과 같게 **종교**를 백엔드에도 더함), 예전 공고 문장 베끼기(띄어쓰기 정리 뒤 40자 연속 일치). 다시 써도 남으면 지금처럼 막지 않고 알린다.
  ④ **관리자 한 칸 다시 쓰기**: `POST /admin/postings/{id}/draft-ai/revise` `{section, note, current}`. 같은 thread(`posting-draft:{공고 id}`)의 체크포인트에서 처음 입력·참고 공고를 읽어 그 칸만 다시 쓰고, 같은 검사를 거친다(요청 1번 + 문제 시 1번 더). 결과는 status 의 `revision` 으로 화면 칸에만 넣고 DB 에는 쓰지 않는다(저장 전 수정 글을 덮지 않게, 관리자가 [임시저장]). 감사 로그 `posting.draft_revise`.
- 계획과 다른 점: 처음에는 그래프를 `interrupt` 로 멈춰 두고 관리자 요청을 기다리려 했으나, 로컬 Python 3.10 에서 interrupt 가 동작하지 않고(실험 확인) 멈춘 작업을 서버에 남기지 않는 편이 단순해, **초안 저장 뒤 그래프는 끝내고 다시 쓰기 때 같은 thread 로 새로 실행**한다.
- 체크포인트는 공고를 게시·삭제하거나 AI 초안을 새로 만들 때 지운다. 상태에는 공고 문장·관리자 입력만 있고 지원자 개인정보는 없다.
- 화면: S-R02 진행 단계를 서버 단계(`stage`)로 표시(참고 공고 찾기 → 초안 작성 → 표현 점검·고쳐 쓰기), S-R03 1단계에 'AI에게 한 칸 다시 쓰게 하기' 상자와 AI 처리 기록(`notes`).
- 개인용 문서 반영: AI 아키텍처(그래프 3개), API 명세서(revise·status), 화면정의서(S-R02·S-R03). 기능정의서(xlsx) JOB-02 는 고치지 않았다.

## C-16. 면접 질문 글 검사 강화 (2026-11-10, 사용자 결정)

- 계기: 질문 DB 있음·없음 시뮬레이션(실제 llm-rt·embed, 지원자 3명 × 2반복)에서 ① 신입에게 이력서에 없는 'pandas 데이터 분석 프로젝트'·'비전 검사 파이프라인 경험'을 물음 ② 직무 질문이 "~구축한 경험이 있으신가요?"처럼 경험을 전제 ③ 찌꺼기("본ly", 끝의 `'}`, ✅) ④ "1문장으로"·"간단히" ⑤ 한 질문에 두세 가지를 물음 ⑥ 지원자2 이력서 질문이 자주 실패.
- ⑥ 원인: 이력서 요약 줄이 `… 40ms 로 줄임 [PyTorch]`처럼 대괄호로 끝나, 근거 구절로 줄을 통째로 옮기던 4B 모델이 `]` 뒤에 `'}`·`✅✅…`·`📌 Note…`를 이어 써 근거 검사에 떨어짐(10번 중 6번, 질문은 멀쩡). 고침: 요약을 `— 사용 기술: PyTorch` 로 바꾸고, 근거는 앞부분이 이력서와 6자 이상 같으면 인정(뒤 찌꺼기 무시), 근거는 10~30자만 옮기게 지시.
- 이력서 질문: 근거는 **경력·프로젝트·자기소개 줄에서만** 인정(학력·기술·자격 제외), 질문에 프로젝트·회사 이름(4자 이상 조각)이 있어야 함(`resume_not_anchored`), 이력서 질문 프롬프트에서 **공고 글을 뺌**(TRD 7-4 ③-3 은 세 가지를 함께 넣는다고 적혀 있음 — 이력서 자리만 예외), 경험 줄이 없으면 AI 를 부르지 않고 예비 질문(`no_resume_experience`).
- 직무 질문: 개념·원리·기준·방법을 묻게 지시하고, 경험을 전제하는 말은 거절(`job_asks_experience`).
- 공통 글 검사(`domain/question_text.py`, 본질문·**꼬리질문 모두**): 끝 찌꺼기는 떼고, 허용 글자(한글·영문·숫자·흔한 문장부호) 밖의 글자·한글에 붙은 영어는 거절(`junk_text`), 답변 방식 지시(문장 수·시간·글자 수·'간단히·짧게·한마디로') 거절, 여러 개 묻기('~했고, ~'·'~이며, ~'·'그리고'·'~와 그 이유'·의문사 2개·물음표 2개) 거절(`compound_question`), 본질문 100자 초과 거절(`too_long`, 꼬리질문은 120자 그대로).
- 요구하는 일 수: TRD 7-4 ④·QST-04 의 '90초면 2개 이하' → **1개**(`MAX_TASKS_PER_ANSWER`).
- 영향: 검사가 엄격해져 AI 질문이 떨어지는 비율과 다시 만드는 횟수가 늘 수 있다(시뮬레이션 결과는 아래 측정).
- 같은 날 다듬은 것(시뮬레이션을 3번 더 돌리며): 질문으로 끝나지 않는 글·서술문에 물음표만 붙인 글("…계기입니다?") 거절(`not_question`), 두 문장 거절, 다시 만들 때 **이전 질문을 함께 보여 주고 고치게** 함(문제만 알리면 '~했고, 그 이유는'을 6번 되풀이), 프롬프트에 **종류마다 다른 질문 꼴** 예시(`KIND_FORMS`, 꼴 하나를 주니 모든 자리가 베낌), 직무 질문의 과거형("…무엇이었나요?")도 경험 질문으로 거절, 인성·회사 질문은 기술 지식을 묻지 않게 지시.
- 측정(llm-rt Qwen3 4B, 지원자 3명 × 질문 DB 있음/없음 × 2반복 = 120자리): AI 가 만든 질문 고치기 전 112 → 1차(규칙만) 74 → 2차(이전 질문 보여 주기) 109 → 3차(종류별 꼴) 110. 3차에서 대신 들어간 10자리 중 8자리는 경험이 없는 신입의 이력서 자리(설계대로 예비 질문). 지원자 1명 질문 10개 17~41초(고치기 전 31~57초). 3차 결과에 찌꺼기·답변 방식 지시·지어낸 경험은 없었다.
- 남은 한계(3차 결과): 예/아니오로 끝나는 인성 질문("의견 차이가 생긴 적이 있나요?") 몇 개, 어색한 말("느꼈는가요", "어떤 기준을 기준으로" 1건), 이력서의 두 항목을 섞은 질문 1건(프로젝트 질문에 경력의 '펌웨어'), 질문은행에서 고른 기존 질문은 이 검사를 거치지 않아 두 가지를 묻는 질문이 1건 나옴.
- 예/아니오 질문(2026-11-10 사용자 결정 "그 이유를 추가로 물어보면 될거같아"): 질문 자체는 그대로 두고(이유를 붙이면 '여러 개 묻기'가 된다) **꼬리질문으로 이유를 묻는다.** 예/아니오 질문 = 의문사(무엇·어떻게·어떤·왜·얼마·언제·어디·누구·뭐·몇)가 없고 부탁하는 꼴(주세요·주시겠어요·말씀해·설명해)도 아닌 질문(`question_text.isYesNo`). 답이 30자보다 짧으면 LLM 없이 "그렇게 답하신 이유를 구체적으로 말씀해 주세요."로 묻고(`engine.yesNoFollowup`, reason_code `vague`), 길면 T4 프롬프트에 "이유·상황이 없으면 vague 로 정하고 그 이유를 물어라"를 덧붙인다. 꼬리질문 개수 제한(질문당 1·종류별 1·전체 4)과 시간 부족(no_time) 건너뛰기는 그대로라, 제한에 걸리면 이유를 묻지 못한다. 질문은행 active 1,914개 중 192개가 예/아니오 질문이다.
- 질문은행 점검(같은 날, 읽기만, 고친 것 없음): 6,420개 중 '여러 개 묻기'로 걸린 것 930개(엑셀 890·AI 생성 38·예비 2), 면접에 쓰이는 active 는 1,914개 중 301개. 걸린 규칙: 의문사 2개 274·두 문장 261·물음표 2개 이상 199·잇는 말 196. 두 문장 가운데 상황 설명 + 질문 하나("…가정해봅시다. 어떻게 검증하시겠습니까?")와 "베이즈 정리와 그 응용을 설명해 주세요", "…점을 보고, …" 는 한 가지를 묻는 것이라 규칙이 지나치게 잡은 경우다(질문은행에 그대로 적용하려면 규칙을 따로 다듬어야 한다). 상황 설명 문장 + 질문 하나와 '…을 보고,' 를 한 가지 질문으로 보도록 다듬어 다시 세면 active 1,914개 중 244개(엑셀 228·AI 생성 16·예비 2). 2026-11-10 사용자 결정: 질문은행·예비 질문의 '여러 개 묻기'는 그대로 둔다(빼거나 고치지 않음)(목록은 시뮬레이션 작업 폴더 `bank_compound_v2.tsv`).

## C-17. 질문 적용 범위와 공고 기반 질문 후보 (2026-11-10, 사용자 결정)

- 결정: 사용자 "권장안으로 진행해보자" — 질문에 적용 범위를 두고, 공고를 게시할 때 그 공고로 질문 후보를 만들어 질문관리에 넣는다. 인터넷 자료를 참고한 후보도 같은 방식으로 넣는다.
- 왜: `questions` 에 공고·직무 칸이 없어 질문은행 대체(`candidates`)가 같은 종류의 active 질문을 **모든 공고에서** 골랐다. 실측: E2E 공고에서 만든 회사 질문("우리 회사가 LLM 기반 서비스를 개발하며 추구하는…", #6343)이 범위 없이 active 라 다른 공고의 회사 자리에도 나갈 수 있었다.
- 스키마(테이블 정의서 4-18 갱신): `questions.posting_id`(FK job_postings, ON DELETE CASCADE, 인덱스) · `questions.job_code`(varchar 32). 둘 다 nullable, 기존 행은 비어 있어 지금과 똑같이 모든 공고에서 쓴다. `migrate.py` ALIGN_STATEMENTS 에 `ADD COLUMN IF NOT EXISTS`.
- 범위 규칙(`question_compose.scopeFor`): 회사 질문 → 그 공고(`posting_id`), 직무 질문 → 그 공고의 직무(`job_code`), 인성 질문 → 공통. `candidates` 는 `posting_id` 가 비었거나 같고, `job_code` 가 비었거나 같은 것만 고른다. 면접 때 만든 질문을 넣는 `savePending` 도 범위를 붙인다.
- 공고 기반 후보(`services/posting_questions.py`): 게시(`POST /admin/postings/{id}/publish`, 이 때문에 async 로 바꿈) 뒤 api 안 백그라운드 작업. 업무·자격·우대 줄(`jobTopics`)마다 직무 질문 1개(최대 6개), 회사 질문 3개. 면접 질문과 같은 `ragPrompt`·`checkGenerated`(글 검사 포함)·다른 회사 이름 검사를 쓰고, 이력서 칸은 '(없음)'(지원자 정보 없음). 자리마다 2번까지(실패하면 이전 질문을 보여 주고 고치게), 시도당 60초. 질문 DB 와 0.8 이상이거나 같은 글이면 넣지 않는다. category '공고 기반', status pending — 관리자가 [추가]해야 쓴다. 실패는 기록만 하고 게시를 막지 않는다. 감사 기록 `question.posting_candidates`.
- 인터넷 참고 후보: `huge/data/web_questions_candidates.json`(65개 — 원문을 옮기지 않고 주제만 참고해 새로 씀, 출처·라이선스 표기, 질문은행 유사도 검사 결과 포함). 컨테이너에 `/data/web_questions.json` 으로 붙이고(compose.app.yml) `python -m app.manage load_web_questions <공고 id>` 가 `verdict=new`(53개)만 category '인터넷 참고', pending 으로 넣는다(같은 글은 건너뜀). 감사 기록 `question.web_candidates`.
- 관리자 질문관리: 목록에 출처 구분(category)과 적용 범위(이 공고만 · 이 직무만 · 공통) 표시. API 명세서에 `GET /admin/questions` 절을 새로 적었다(그전에는 명세에 없었다).
- 그대로 둔 것: 엑셀 질문은 범위가 비어 있어(모든 직무) 다른 직무 공고가 열리면 ML 질문이 섞일 수 있다 — 지금 열린 직무가 AI/AX 하나뿐이라 그대로 두었다. RAG 예시 검색(`rag.similar`)은 엑셀 질문만 보므로 범위와 무관하다.
- 문서 충돌(해결, 2026-11-10 사용자 결정): 화면정의서 v0.7 은 "문제은행·예비 질문 관리 화면은 두지 않는다(2026-10-28 팀 결정)" 였는데 코드에는 그전부터 관리자 질문 관리 화면(`/admin/questions`, AI 생성 질문 검토)이 있었다. 사용자: 있는 화면을 문서에 넣는다 → 화면정의서에 S-R11 질문 관리(§10.11)를 새로 적고, 문항 현황 줄은 '엑셀 문제은행·예비 질문·코딩 문제는 명령어로, AI 가 만든 질문 검토는 S-R11'로 고쳤다.
- 범위 미리 붙이기 (같은 날, 사용자 허용 "적용범위를 미리 만들어둬도 되고"): 범위 열이 생기기 전에 만든 AI 직무 질문 125개(사용 중 26 · 검토 대기 94 · 제외 5)에 `job_code='AI_AX'` 를 붙였다. 지금까지 공고가 모두 AI_AX 라 이 질문들은 모두 AI_AX 공고에서 나왔다. 회사 질문 #6400 은 출제 기록으로 'AI/AX 엔지니어 (신입)' 공고에서 나온 것을 확인해 그 공고에 붙였다. DB 직접 수정(한 번), 감사 기록 `question.scope_backfill`. 나머지 범위 없는 AI 회사 질문 11개(사용 중 7, 검토 대기 4)는 만든 공고가 지워져 알 수 없어 그대로 둔다(→ 아래 '알린 문제').
- 회사 질문 프롬프트 다듬기 (같은 날, 사용자 요청): 실측 후보가 "…문화에 어떻게 매력을 느꼈는가요?"(어색한 말끝), "우리 회사의 제품 개발 환경에서 가장 감명받은 경험은?"(입사 전 지원자에게 회사 안 경험을 물음)이었다. ① 글 검사에 `awkward_ending`('~는가요'·'~싶은가요'로 끝남, 모든 종류) ② 회사 질문 검사 `company_asks_inside`('우리 회사의/에서 … 경험·겪·감명') ③ 회사 질문 안내에 "지원자는 아직 입사 전이다 — 공고에서 읽은 일·문화를 두고 지원 이유·생각·입사 뒤 하고 싶은 일을 묻는다", 꼴 예 2개 추가, 말끝 안내 ④ 공고 기반 회사 질문 3자리에 서로 다른 초점(`COMPANY_ANGLES`: 지원 동기 · 회사가 하는 일과 직무 이해 · 조직 문화와 일하는 방식). 실측(llm-rt, 15자리 2번): 어색한 말끝·회사 안 경험 0건. 버려진 자리는 대부분 이미 있는 후보와 겹침(0.8 이상)이었다. 남은 한계: 면접관이 '제가'라고 쓴 질문 1건.
- 알린 문제 (사용자 요청 "범위 없이 쓰더라도 문제가 생기면 알려줘", 2026-11-10 확인): ① 사용 중인 AI 질문 43개 중 19개가 오늘 글 검사에 걸린다(두 가지 묻기 17, 답변 방식 지시 2 — 검사가 생기기 전에 승인된 것). ② 범위 없는 AI 회사 질문 가운데 지워진 공고의 서비스를 적은 것이 있다(#6389 '면접 프로세스 개선', #6407 'AI 기반 자동 테스트 서비스', 검토 대기). 다른 공고 면접에 나가면 맞지 않는다. 상태는 바꾸지 않았다 — 사용자 판단.
- 처리 (같은 날, 사용자 결정 "그래 일단 그렇게 해주고"): 위 ①의 사용 중 19개는 [빼기], ②의 검토 대기 2개(#6389·#6407)는 [제외] — 모두 `rejected`. 관리자 [빼기]와 같게 질문마다 감사 기록 `question.reject`(사유 포함)를 남겼다(DB 한 트랜잭션, 진행 중 면접 없음 확인). 질문 관리 '제외' 탭에서 [추가]로 되돌릴 수 있다. 이제 사용 중인 AI 질문은 24개(직무 19, 인성 5)이고 AI 회사 질문은 사용 중 0개다(회사 자리는 엑셀 회사 질문 15개·예비 5개로 대체된다).
