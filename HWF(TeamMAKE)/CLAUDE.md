# AI 1차 채용면접 자동화 플랫폼 — 프로젝트 개발 지침서

## 1. 프로젝트 개요

본 프로젝트는 AI를 활용하여 채용공고 작성, 지원자 관리, 1차 면접, 코딩테스트, 평가 및 결과 확인을 지원하는 **AI 기반 채용면접 자동화 플랫폼**을 개발하는 것을 목표로 한다.

현재 프로젝트는 공통 기획 및 설계 문서 작성 단계를 거쳐 프로그램 구현 단계로 전환하였다.

### 1.1 개발 진행 원칙

- 프로젝트의 기획 및 설계 문서는 팀원들이 공통으로 작성하고 관리한다.
- 프로그램 구현은 우선 각 팀원이 독립적으로 진행한다.
- 개인별 기술 선택과 구현 방식은 서로 다를 수 있다.
- 이후 구현 결과를 비교하고, 완성도와 안정성이 높은 방식을 검토하여 공동 개발 방향을 결정한다.
- 공통 설계 문서는 개발의 기준으로 활용하지만, 기술적 문제나 설계상 결함이 확인되면 수정할 수 있다.
- 설계 변경은 개발자가 임의로 결정하지 않고 사용자와 협의하여 진행한다.

**핵심 원칙: 설계 문서를 존중하되, 구현 가능성과 안정성을 우선 검증한다.**

### 2.2 문서 검토 원칙

구현을 시작하기 전에 관련 문서를 검토하고 다음 사항을 확인한다.

1. **설계 일치성:** 구현하려는 기능이 PRD, TRD 및 기능정의서와 일치하는가?
2. **기술 실현 가능성:** 현재 개발 환경과 기술 스택에서 구현할 수 있는가?
3. **문서 정합성:** 서로 다른 문서에 모순이나 누락이 존재하는가?
4. **성능 및 안정성:** 구현 시 과부하, 응답 지연, 오류가 발생할 가능성이 있는가?
5. **추가 기능 필요성:** 필수 기능이 누락되었거나 개선이 필요한가?

검토 과정에서 문제가 발견되면 해당 문서와 항목을 명시하고 사용자에게 보고한다.

### 2.3 문서 간 충돌 처리

문서마다 역할이 다르므로 모든 문서에 일률적인 우선순위를 적용하지 않는다.

기본적으로 다음 기준을 적용한다.

| 판단 대상 | 우선 참고 문서 |
|---|---|
| 서비스 목표 및 요구사항 | PRD |
| 기능 동작 및 조건 | 기능정의서 |
| 기술 스택 및 구현 조건 | TRD |
| 화면 구성 및 UI 동작 | 화면정의서 |
| API 계약 | API 명세서 |
| 데이터베이스 구조 | 테이블 정의서 |
| 사용자 진행 순서 | 시나리오 및 플로우차트 |
| AI 처리 구조 | AI 기술 아키텍처 |

동일한 사항에 대해 문서 간 내용이 충돌하는 경우 다음 절차를 따른다.

1. 충돌하는 문서와 해당 내용을 식별한다.
2. 문서의 버전과 작성 목적을 확인한다.
3. 각 설계의 차이와 구현 영향을 분석한다.
4. 권장 해결 방안을 제시한다.
5. 사용자에게 최종 판단을 요청한다.
6. 승인된 방향으로 구현한다.

**명시적인 승인 없이 문서 간 충돌을 임의로 해결하지 않는다.**

단, 이미 승인된 규칙으로 해결할 수 있는 단순한 표현 차이는 별도의 승인 없이 정리할 수 있다.

## 3. 핵심 서비스 구현 범위

### 3.1 주요 기능

프로젝트는 다음 기능을 중심으로 구현한다.

1. 회원가입 및 로그인
2. 관리자 및 지원자 권한 구분
3. AI 기반 채용공고 생성 및 관리
4. 채용공고 조회 및 지원
5. 지원자 마이페이지
6. AI 면접 진행
7. 질문 생성 및 질문은행 관리
8. 음성 인식 및 음성 합성
9. 면접 답변 분석 및 평가
10. 선택형 코딩테스트
11. 면접 결과 리포트
12. 관리자 평가 결과 조회 및 관리

구현 세부사항은 관련 설계 문서를 기준으로 결정한다.

### 3.2 AI 기능 구현

AI 관련 기능은 AI 기술 아키텍처 문서를 우선 참고한다.

RAG, LangChain, LangGraph, LLM, STT, TTS, 벡터 데이터베이스 등의 기술은 해당 기능에 실제로 필요한 경우에 사용한다.

기술 사용 자체를 목표로 삼지 않는다.

예를 들어 단순한 데이터 조회는 일반적인 데이터베이스 쿼리로 해결할 수 있다면 불필요하게 LLM을 사용하지 않는다.

AI 기반 평가 기능은 평가 근거를 기록하고, 평가 결과의 일관성과 재현 가능성을 검증할 수 있도록 설계한다.

시선, 표정, 음성 등의 비언어적 정보는 기술적 정확도와 공정성을 검토한다. 직무 능력과의 관련성이 입증되지 않은 특징을 채용 합격·불합격 판단의 직접적인 근거로 사용하지 않는다.

### 3.3 코딩테스트 구현

코딩테스트는 모든 공고에 의무적으로 적용하지 않는다.

관리자가 공고 생성 또는 수정 시 코딩테스트 적용 여부를 선택할 수 있도록 구성한다.

- 관리자 공고관리 화면에 코딩테스트 적용 토글을 제공한다.
- 토글이 활성화된 공고에만 코딩테스트를 적용한다.
- 비활성화된 공고는 코딩테스트 단계를 건너뛴다.
- 세부 시험 흐름과 평가 방식은 코딩테스트 관련 설계 문서를 따른다.

코딩테스트의 실제 코드 실행은 격리된 실행 환경에서 수행하도록 설계한다.

## 4. 구현 제한사항

### 4.1 현실적인 구현 우선

사용자 경험을 심각하게 저해하거나 기술적으로 실현하기 어려운 기능은 무리하게 구현하지 않는다.

다음 절차를 따른다.

1. 문제가 발생하는 원인을 분석한다.
2. 기존 기술로 해결 가능한지 확인한다.
3. 성능과 안정성을 유지할 수 있는 대체 방법을 검토한다.
4. 대체 방법의 장점과 단점을 비교한다.
5. 적절한 해결책이 없다면 구현이 어렵다는 사실을 명확하게 보고한다.

기능을 구현할 수 있다는 이유만으로 무조건 구현하지 않는다.

### 4.2 성능 및 자원 관리

다음 항목을 고려한다.

- LLM 응답 시간과 토큰 사용량
- STT 및 TTS 처리 지연
- 영상 및 음성 데이터 전송 부하
- GPU 및 CPU 사용량
- 데이터베이스 조회 성능
- 동시 사용자 처리 가능성
- 외부 API 장애 및 호출 제한

과부하가 예상되면 비동기 처리, 캐싱, 작업 큐, 모델 경량화 등의 대안을 검토한다.

단, 실제 필요성이 확인되지 않은 최적화는 미리 구현하지 않는다.

### 4.3 보안 및 개인정보

본 프로젝트는 채용 지원자의 개인정보와 면접 데이터를 처리하므로 다음 원칙을 준수한다.

- 사용자 권한에 따른 접근 제한
- 비밀번호의 안전한 해시 저장
- API 인증 및 인가 검증
- 민감정보의 불필요한 로그 기록 금지
- 음성 및 영상 데이터 접근 통제
- 개인정보 수집·보관·삭제 정책 검토
- 사용자 입력 및 업로드 파일 검증
- 코딩테스트 실행 환경 격리
- LLM 프롬프트 인젝션 및 정보 유출 위험 검토

보안상 중대한 문제가 발견되면 해당 구현을 중단하고 우선 보고한다.

## 5. 코딩 규칙

### 5.1 기본 작성 규칙

- 들여쓰기는 공백 4칸을 사용한다.
- Python 함수 및 변수는 프로젝트 규칙에 따라 `camelCase`를 사용한다.
- 클래스 이름은 `PascalCase`를 사용한다.
- 상수는 `UPPER_SNAKE_CASE`를 사용한다.
- 외부 라이브러리 및 프레임워크가 요구하는 명명 규칙은 예외로 한다.
- 기존 코드의 명명 규칙과 충돌하는 경우 사용자에게 확인한다.
- 함수는 하나의 명확한 책임을 갖도록 작성한다.
- 중복 코드는 필요한 범위에서만 제거한다.
- 불필요한 추상화와 복잡한 설계를 피한다.
- 주석은 코드 자체로 설명하기 어려운 의도나 제약사항에 작성한다.

### 5.2 SDD 및 TDD 적용

본 프로젝트는 SDD(Specification-Driven Development)와 TDD(Test-Driven Development)를 함께 활용한다.

**SDD 절차**

1. 관련 설계 문서를 확인한다.
2. 기능의 요구사항을 구체화한다.
3. 입력값, 출력값, 예외 조건을 정의한다.
4. 완료 기준을 확정한다.
5. 해당 명세를 기준으로 구현한다.

**TDD 절차**

1. 기능의 기대 동작을 테스트로 작성한다.
2. 테스트가 실패하는지 확인한다.
3. 테스트를 통과하는 최소한의 코드를 작성한다.
4. 테스트를 재실행한다.
5. 필요한 경우 리팩터링한다.
6. 기존 기능에 회귀 오류가 없는지 확인한다.

TDD 적용이 어려운 UI, 외부 AI 서비스 및 장치 연동 기능은 통합 테스트나 수동 검증으로 보완한다.

## 6. 개발 작업 절차

AI 개발 에이전트는 다음 순서로 작업한다.

### 1단계: 요구사항 확인

사용자의 요청과 관련 문서를 확인한다.

요구사항이 불명확하거나 문서 간 충돌이 발생하면 질문한다.

### 2단계: 구현 계획 수립

코드를 작성하기 전에 다음 사항을 간단히 제시한다.

- 구현할 기능
- 참고 문서
- 수정하거나 생성할 파일
- 적용할 기술
- 예상 문제점
- 검증 방법

### 3단계: 구현

승인된 요구사항을 기준으로 최소한의 코드를 작성한다.

기존 기능을 불필요하게 수정하지 않는다.

### 4단계: 검증

단위 테스트, 통합 테스트, 형식 검사 등을 수행한다.

오류가 발생하면 원인을 확인하고 수정한다.

### 5단계: 결과 보고

작업이 끝나면 다음 내용을 보고한다.

- 구현 완료 기능
- 생성 및 수정 파일
- 실행한 테스트
- 테스트 결과
- 미해결 문제
- 다음 작업 제안

테스트를 실행하지 않았다면 실행하지 않았다고 명시한다.

## 8. 설계 변경 및 추가 기능 제안

AI 개발 에이전트는 설계 개선을 제안할 수 있으나, 승인 없이 기능을 추가하거나 기존 설계를 변경해서는 안 된다.

추가 기능이 필요하다고 판단되면 다음 형식으로 보고한다.

| 항목 | 설명 |
|---|---|
| 제안 기능 | 추가하려는 기능 |
| 제안 이유 | 현재 설계의 문제점 또는 필요성 |
| 기대 효과 | 성능, 편의성, 안정성 등 |
| 기술적 위험 | 구현 난이도 및 예상 오류 |
| 영향 범위 | 수정이 필요한 코드와 문서 |
| 권장 여부 | 필수 / 권장 / 선택 |

제안과 실제 구현은 구분한다.

사용자가 승인한 기능만 구현한다.

단, 요청된 기능을 정상적으로 구현하기 위해 반드시 필요한 내부 수정은 범위를 설명한 후 진행할 수 있다.

## 9. AI 개발 에이전트 행동 원칙

다음은 Andrej Karpathy의 실용적 코딩 철학을 참고하여 프로젝트에 맞게 정리한 행동 원칙이다.

### 9.1 Think Before Coding — 코딩 전에 생각하라

추측에 기반하여 코드를 작성하지 않는다.

- 구현 전에 가정을 명확하게 밝힌다.
- 요구사항이 불명확하면 질문한다.
- 여러 해석이 가능하다면 차이를 설명한다.
- 더 단순한 해결 방법이 있다면 제시한다.
- 기존 설계에 문제가 있다면 근거를 들어 이의를 제기한다.
- 핵심 요구사항이 불명확하면 구현을 보류한다.

단, 명확하고 위험성이 낮은 작업은 불필요한 확인 없이 진행할 수 있다.

### 9.2 Simplicity First — 단순함을 우선하라

문제를 해결하는 데 필요한 최소한의 코드를 작성한다.

- 요청하지 않은 기능을 추가하지 않는다.
- 불필요한 추상화를 만들지 않는다.
- 실제로 필요하지 않은 확장 기능을 구현하지 않는다.
- 과도한 예외 처리와 복잡한 설계를 피한다.
- 간단한 방법으로 해결할 수 있다면 우선 검토한다.

다만 보안, 데이터 무결성 및 필수 예외 처리를 단순화를 이유로 생략하지 않는다.

### 9.3 Surgical Changes — 필요한 부분만 수정하라

요청과 직접적으로 관련된 코드만 수정한다.

- 정상적으로 동작하는 코드를 불필요하게 변경하지 않는다.
- 관련 없는 주석이나 코드 스타일을 수정하지 않는다.
- 기존 프로젝트의 구조와 스타일을 존중한다.
- 기존에 존재하던 미사용 코드는 임의로 삭제하지 않는다.
- 자신의 수정으로 발생한 미사용 코드는 정리한다.

변경된 코드가 요청사항과 어떤 관련이 있는지 설명할 수 있어야 한다.

### 9.4 Goal-Driven Execution — 검증 가능한 목표를 설정하라

모든 구현 작업은 명확한 성공 기준을 갖는다.

예시:

**기능 구현**

- 목표: 지원자 로그인 기능 구현
- 성공 기준: 올바른 계정으로 로그인 가능
- 실패 기준: 잘못된 계정 정보는 인증 거부
- 검증: 인증 단위 테스트

**버그 수정**

- 목표: 면접 녹음 중복 실행 오류 수정
- 성공 기준: 중복 녹음 스트림이 생성되지 않음
- 검증: 오류 재현 및 수정 후 재검증

**리팩터링**

- 목표: 중복 코드 제거
- 성공 기준: 기존 기능과 동작이 동일함
- 검증: 변경 전후 테스트 통과

모호한 목표를 그대로 구현하지 않는다.

## 10. AI 개발 에이전트 보고 원칙

개발 중 다음 상황이 발생하면 사용자에게 보고한다.

### 즉시 보고가 필요한 상황

- 설계 문서 간 중대한 충돌
- 핵심 기능 구현 불가능
- 심각한 보안 취약점
- 기존 기능에 영향을 주는 구조 변경
- 데이터베이스 스키마 변경 필요
- 핵심 기술 스택 변경 필요
- 평가 기준 또는 채용 판정 로직 변경 필요

### 일반 작업 보고

일반적인 기능 구현과 오류 수정은 작업 단위로 결과를 보고한다.

사소한 내부 구현 선택까지 매번 승인받을 필요는 없다.

### 보고의 정확성

- 실제로 확인하지 않은 사실을 확정적으로 표현하지 않는다.
- 실행하지 않은 테스트를 통과했다고 보고하지 않는다.
- 구현되지 않은 기능을 완료했다고 표시하지 않는다.
- 추정과 검증된 사실을 구분한다.
- 오류를 숨기기 위해 임시 코드를 추가하지 않는다.

## 11. 최종 개발 원칙

본 프로젝트는 단순히 많은 기능을 구현하는 것이 목적이 아니다.

**설계 문서에 기반하여 실제로 동작하고, 검증 가능하며, 안정적으로 운영할 수 있는 AI 채용면접 플랫폼을 만드는 것이 목표다.**

따라서 다음 원칙을 최우선으로 한다.

1. 설계 문서를 먼저 확인한다.
2. 구현 가능성을 검토한다.
3. 명확한 목표를 설정한다.
4. 필요한 기능만 구현한다.
5. 테스트로 동작을 검증한다.
6. 문제점과 한계를 정확하게 보고한다.
7. 설계 변경은 사용자와 협의한다.
8. 검증된 결과를 바탕으로 다음 개발을 진행한다.

**문서에 없는 내용을 임의로 확정하지 말고, 구현할 수 없는 기능을 억지로 만들지 말며, 실제 동작 여부를 검증한 결과로 판단한다.**
