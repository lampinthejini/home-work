- 대상: `Final_Project_PRD_v1.6.pdf` (2026-10-29), `Final_project_테이블정의서.pdf` (수정본, 기준 API 명세서 v1.1 + TRD v1.5)

- 비교 기준: TRD v1.5 · 화면정의서 v0.5 · API 명세서 v1.1 · 기술아키텍처 v1.1

## 0. 총평

**PRD v1.6**은 TRD 검토 결정을 잘 반영했습니다. 아래 항목이 이제 TRD·화면정의서와 같습니다.

- AI 판정은 시스템이 형식·근거만 확인하고 합격 기준으로 다시 판정하지 않음 (1-3 ②, EVL-05, AC-13)
- '대기'는 상태가 아니라 안내 화면 (INT-08, 6-2)
- 화면 이탈 1번째는 남은 답변 시간부터 이어서 (CHT-02, AC-11)
- 연결이 끊긴 순간 장애 판단, 창 닫기는 바로 응시 종료 (7-2)
- 접속 범위 127.0.0.1, 기준 PC (10-1, 10-3, C-20)
- 답변 실시간 자막 (INT-02)
- 꼬리질문 판단 시간·다음 질문 목표 시간은 기준 PC에서 재서 정함 (INT-06, 10-3)

다만 **고치다 남은 곳**이 문서 안에 몇 군데 있어 PRD 안에서 서로 다른 말을 합니다(1장).

**테이블정의서 수정본**은 지난 검토 의견을 모두 반영했습니다(값 이름 API와 통일, user_resumes·resume_uploads·recordings·posting_revisions 추가, contact_email, memos.updated_at, consents 증거 보존, 탈퇴 시 행 삭제, Redis 5장). 남은 것은 API 명세서 v1.1에서 그대로 따라온 옛 결정 2개와, PRD v1.6이 정한 보관 기간 반영입니다(2장).

### 2-3. 탈퇴 시 다른 테이블 처리 (팀 결정 필요)

공통 규칙 7은 "탈퇴하면 users 행을 바로 지운다"인데, users를 가리키는 칸들이 어떻게 되는지가 없습니다. `applications.applicant_id`는 NOT NULL이라 정하지 않으면 **탈퇴 자체가 FK 오류로 실패**합니다.

| users를 가리키는 칸 | 제안 |
|---|---|
| `applications.applicant_id` | **CASCADE** (지원 건과 그 아래 면접 데이터까지 즉시 삭제, deletion_logs `cause = withdraw`). PRD 10-2 "탈퇴하면 바로 지움(진행 중 응시는 취소)"과 맞음 |
| `user_resumes.user_id` · `resume_uploads.user_id` · `notifications.user_id` | CASCADE |
| `consents.user_id` | 이미 SET NULL (subject_hash로 증거 유지) — 그대로 |
| `audit_logs.actor_id` · `app_settings.updated_by` · `app_setting_history.changed_by` | SET NULL (관리자만 해당, 관리자는 탈퇴 없음) |

**팀에 물어볼 점**: 탈퇴하면 이미 결과가 나온 지원 건(공개 후 7일 안)도 바로 지우는지. PRD 10-2는 '회원 계정 정보'만 "탈퇴하면 바로 지움"이고 '면접 데이터'는 "결과 공개일부터 7일"이라 둘이 겹칩니다. 개인정보 원칙상 **바로 지우는 쪽(CASCADE)을 추천**합니다. 관리자 입장에서는 2차로 넘길 사람이 목록에서 사라질 수 있다는 점이 리스크입니다.

### 2-4. 아직 열려 있는 것

- 4-7 `evaluation_criteria.coding_enabled` 기본값 "팀 확정 필요" — PRD v1.6 JOB-03에도 기본값이 없습니다. 팀이 정해 PRD JOB-03·화면정의서 S-R03·테이블정의서에 같이 적어야 합니다.
