# 면접 질문 품질 기준 (v1.0, 2026-11-20)

AI가 만든 면접 질문이 **좋은 질문인지 재는 기준**이다. 지원자를 채점하는 기준(`평가_기준.md`)과는 다르다. 이 문서는 지원자에게 던지는 질문 자체를 본다.

- 관련: CONFLICTS C-29, 논의사항 19, 정답 채점·스크립트·결과는 `개인용/_work/질문품질/`
- 사용자 결정(2026-11-20): 사람이 따로 검토하지 않는다. 이 기준과 4B 채점(가르친 결과)으로 진행한다.

---

## 1. 무엇을 보려는가

형식적이고 누구에게나 하는 질문보다, 아래 세 가지를 확인할 수 있는 질문이 좋은 질문이다(사용자, 2026-11-20).

1. 지원자가 **자기가 쓴 내용을 잘 아는지**
2. **회사에 얼마나 관심이 있는지**
3. **실무 정보를 잘 활용하는지**

자료(공고·이력서·회사 정보·기술 글)는 넓게 모아 둔다. 다만 질문 한 자리에 넣는 자료는 **공고·이력서를 포함해 3개까지**로 한다(2026-11-20 결정, 아직 구현하지 않음). 자료가 많으니 한 질문에 쓰이는 자료가 적은 것은 문제가 아니다. 자료 반영률은 기록만 하고 목표로 삼지 않는다.

## 2. 1단계: 불량 검사 (하나라도 걸리면 불량)

| 코드 | 불량 | 예 |
|---|---|---|
| **B1** | **틀린 전제**. ① 지원자 본인의 일(서류의 프로젝트·업무·연구)에 서류에 없는 실패·실수·사건을 붙여 말함 ② 같은 갈래가 아닌 두 가지를 '차이·구분'으로 비교함 ③ 회사 정보와 틀린 사실 | ① "LLM을 활용한 분석 보고서를 만들 때 실패한 경험에서…"(서류에는 해 봤다는 것만 있음) ② "LangChain에서 벡터 DB와 RAG의 역할을 구분할 때…"(저장소 ↔ 방식) ③ AIIT 서비스 목록에 없는 이름을 AIIT 서비스라고 말함 |
| **B2** | 차별·사생활 (나이·결혼·출산·출신·종교·건강) | "결혼 뒤에도 야근이 많은 업무를 계속하실 수 있나요?" |
| **B3** | 특정 글·자료를 **읽었는지** 묻기 | "기술 블로그의 ○○ 글을 읽어 보셨나요?" |
| **B4** | 문장 깨짐: 말끝이 깨짐, 같은 말 반복, 뜻이 통하지 않음, 면접 존댓말로 어색한 말끝 | "…활용하셨는가요~인가요?", "Python과 파이썬의…", "…스펙 주도 개발 방식과의 연계성에 대한 장점과 단점" |

알아 둘 것:
- **누구에게나 묻는 일반 가정은 B1이 아니다.** "실패한 경험이 있다면", "팀 프로젝트에서 의견이 달랐을 때"는 괜찮다.
- **본인 일에 실패를 붙이고 싶으면** 서류에 실패가 적혀 있을 때만 그렇게 묻는다. 없으면 이렇게 묻는다: "그 일에서 **부족했던 부분은 무엇이었고**, 그걸 바탕으로 어떻게 성장했나요?" (사용자, 2026-11-20)
- **질문이 답을 요구하는 부분은 전제가 아니다.** "어떤 기준을 썼나요", "놓친 것은 없었나요"가 그렇다.
- **영어 뒤 조사 하나 틀린 것은 B4가 아니다.** 'LangChain를' 같은 것은 코드가 고친다.
- **'한 가지만 묻기'는 기준이 아니다.** 2026-11-16에 없앴다(C-19). 요구하는 일은 2개 이하면 된다.
- 처음 초안의 B2 '한 질문에 하나만 묻는다'를 빼면서 번호를 다시 매겼다.

## 3. 2단계: 질 점수 (1~5점, 2·4점은 그 사이)

점수는 **질문 글에 적힌 말로만** 매긴다. 지원자 서류에 관련 경험이 있다는 이유로 점수를 올리지 않는다.

### Q1 맞춤도: 이 사람·이 공고라서 나온 질문인가

| 점수 | 기준 | 예 |
|---|---|---|
| 5 | 특정 프로젝트·업무(이름이나 무엇을 만들었는지)와 그 안의 구체 요소(방법·도구·수치·결정·겪은 일)가 함께 있음 | "사내 규정 검색 챗봇에서 **BM25**와 문단 단위 검색을 결합한 이유" |
| 4 | 특정 프로젝트·업무만 있음 | "LLM을 활용한 분석 보고서를 만들 때…" |
| 3 | 공고·회사 말이 있음: LLM 기반 서비스·RAG·사내 문서·AI 도입·LangChain·벡터 DB·AI/AX 엔지니어, AIIT 서비스·AIIT-X·가치·인재상·문화·일하는 방식·AI 구조 | "RAG 파이프라인에서 검색된 문서의 관련성을 어떻게 측정하나요?" |

### Q3 연결: 회사·공고 업무와 잇는가

먼저 볼 것이 셋 있다.
- 기술 지식(원리·정의·차이·장단점)을 묻는 질문이면 1점이다.
- 의견을 묻는 질문은 많아야 3점이다.
- 지원자 본인의 과거 프로젝트 안의 문제·선택은 회사 상황이 아니다. 이런 질문은 2점이다.

## 4. 4B에게 맡기는 방법 (프롬프트로 가르침)

사용자 결정(2026-11-20): 모델을 다시 학습하지 않고 **기준 + Claude가 채점한 예시를 프롬프트에 넣어** 가르친다. 합격선은 **Q1~Q3 ±1 이내 90%, 불량 놓침 0**이다.

| 단계 | 누가 | 무엇을 | 왜 |
|---|---|---|---|
| ① 코드 글 검사 | `question_text.textProblem`·`dropDoubledName` | 말끝 깨짐·물결표·어색한 말끝·같은 이름 두 번 → B4 | 4B·8B 모두 문체를 거의 못 알아봄. 규칙으로 되는 일은 규칙으로 (CLAUDE.md 3.2) |
| ② 호출 A | 4B, **질문 글만** | Q1·Q2·Q3, B1(비교)·B2·B3·B4 | 서류를 같이 주면 "질문이 서류를 짚었나"가 아니라 "서류에 경험이 있나"로 점수를 매김(1차 Q1 65%) |
| ③ 호출 B | 4B, **서류와 함께**, 인성·이력서 질문만 | 질문이 일어난 일로 말하는 사건이 서류에 있나 → 없으면 B1 | 전제는 서류가 있어야 판단 가능 |

- 프롬프트: 기준(위 2·3장을 줄인 것) + 공고·회사 요약 + Claude 채점 예시 13개 (`grade4b.py` 의 `SYSTEM_A`·`SYSTEM_B`·`EXAMPLES`). 온도 0, JSON 스키마로 답을 받는다. `why`(근거)를 점수보다 먼저 쓰게 한다.
- 길이: 호출 A 약 3,200토큰. llm-rt 한 자리 한도(4,096)에 들어간다.

## 5. 결과 (2026-11-20)

### 정답 채점 (Claude)

모의 지원 2번(11-19)의 실제 질문 108개에 기준 예시 10개(4·5점과 불량이 드물어 직접 씀)를 더해 **118개**를 채점했다. 그중 불량은 15개다. 13개는 프롬프트 예시로 쓰고 **105개로 시험**했다.

### 4B 일치율

| 항목 | 1차 (서류 함께) | 2차 (호출 둘로) | 3차 (규칙 다듬기) | **최종 (+코드 말끝 2꼴)** | 합격선 |
|---|---|---|---|---|---|
| Q1 ±1 이내 | 65% | 88% | 88% | **88%** | 90% ✗ |
| Q2 ±1 이내 | 80% | 95% | 95% | **95%** | 90% ✓ |
| Q3 ±1 이내 | 89% | 87% | 91% | **91%** | 90% ✓ |
| 불량 놓침 (12개 중) | 7 | 7 | 7 | **5** | 0 ✗ |
| 불량 아닌데 불량 | 0 | 3 | 2 | **2** | — |

최종 결과에서 아직 놓치는 불량 5개입니다.
- 서류에 없는 실패 3개(1-p5-1, 2-p3-9, 2-p10-9)
- 비교할 수 없는 두 가지 1개(2-p10-7)
- 뜻이 통하지 않음 1개(2-p1-6)

전제 판단(호출 B)은 같은 질문도 시험마다 결과가 달라졌다(2-p10-9를 2차엔 잡고 3차엔 놓침). 더 손보면 오히려 꼬일 수 있어 **여기서 멈춘다**(사용자, 2026-11-20).

### 시간 (기준 PC, llm-rt GPU, 한 번에 하나)

| | 값 |
|---|---|
| 질문 하나 | 평균 **2.1초**, 90%는 3.4초 안 (인성·이력서는 호출 2번) |
| 면접 한 건 (10문항) | 약 **20~25초** |
| 105문항 | 3분 37초 |

llm-rt는 질문 만들기·꼬리질문과 같은 모델을 쓴다. 그래서 면접 중에 이 채점을 돌리면 서로 밀린다. 지금은 측정용(질문을 다 만든 뒤 따로)으로만 쓴다. 정확도를 지키면서 더 빠르게 만드는 일은 하지 않았다(사용자: "일단 여기까지").

### 8B 문체 다듬기 시험 (쓰지 않기로 함)

질문을 만든 뒤 8B(llm-eval, CPU)가 문체를 다듬게 하는 방법도 118개로 시험했다.

| 본 것 | 결과 |
|---|---|
| 문체 불량 5개 | 3개를 문제로 표시했지만 실제로 고친 건 1개. 그 하나도 코드 규칙이 이미 고치는 것 |
| 뜻이 통하지 않는 문장 | 못 잡음 |
| 멀쩡한 질문 | 약 35개에 "말끝이 깨짐"이라고 잘못 표시 |
| 질문을 망가뜨림 | **3개에서 앞부분(회사 상황)을 잘라 냄** |
| 시간 | 질문 하나 평균 12.7초, 면접 한 건 약 2분. llm-eval은 채점에도 써서 서로 밀림 |

결론: 쓰지 않는다. 문체는 코드 규칙으로만 처리한다. 11-19에 4B 다듬기를 시험했을 때도 50개 중 0건을 고쳤다(C-28).

### 질문 자리 자료를 바꾼 전후 (C-30·C-31, 7명 × 3세트 = 질문 210개)

| 자리 | Q1 전→후 | Q2 전→후 | Q3 전→후 | 불량 전→후 |
|---|---|---|---|---|
| 회사 | 2.95 → 3.26 | 1.27 → 2.03 | 3.05 → 3.28 | 0 → 0 |
| 직무 | 2.99 → 2.77 | 1.82 → 1.81 | 1.98 → 1.69 | 8 → 6 |

'후'는 C-31 1차(칸 안에서 가장 가까운 항목 하나). 회사 질문의 '사용자 중심' 변형이 42개 중 19개 → 4개로 줄었다. 직무 Q3 이 떨어진 원인(상관없는 소식, 같은 항목 반복, 한 줄 두 말의 '차이')은 CONFLICTS C-31 에서 고쳤다.

## 6. 한계

- 정답 채점은 Claude 한 사람의 판단이다. 애매한 것도 있다. 예를 들어 '검수 과정과 답변 생성 과정의 차이'는 비교할 수 있다고 봤다.
- 샘플은 공고 하나(AI/AX 엔지니어)와 지원자 6명뿐이다. 다른 직종에 쓰려면 3장의 공고·회사 말 목록을 그 직종에 맞게 바꿔야 한다.
- 4·5점 질문은 실제 생성 질문에 거의 없어서 Claude가 직접 쓴 예시로 채웠다. 실제 질문이 이 점수에 이르는지는 아직 재지 않았다.
- 4B는 Q1이 88%로 합격선에 2%p 모자라고, 불량 5개를 놓친다. 그래서 **질문 하나하나를 거르는 문지기로는 아직 믿기 어렵다.** 많은 질문의 경향을 보는 용도(질문 만들기를 바꾼 전후 비교)에 맞다.

|---|---|
| `_work/질문품질/build_labels.py` → `labels.jsonl` | Claude 정답 채점 118개(근거 포함) |
| `_work/질문품질/grade4b.py` | 4B 채점(최종). `grade4b_v1.py`·`grade4b_v2.py`는 1·2차 |
| `_work/질문품질/polish8b.py` | 8B 문체 다듬기 시험 |
| `_work/질문품질/r1_v1·r2_v2·r3·final.jsonl`, `final_summary.json`, `p1.jsonl` | 결과 |
| `_work/질문품질/grade_new.py`, `실측_1120/` | 새 질문 채점(정답 없이), 7명 × 3세트 실측(`sets3.py`, 결과 `sets3_*`·`c31_*`·`c31b_*`, 보기 `*_view.md`) |
| `_work/질문품질/원본_1119/` | 모의 지원 결과 2회·지원자 서류(지어낸 사람)·모의 공고 스크립트 |

돌리기: `docker cp 개인용/_work/질문품질 huge-app-api-1:/tmp/qq` 다음에 `docker exec -w /tmp/qq huge-app-api-1 python grade4b.py --out /tmp/결과.jsonl`. 컨테이너에 옛 `/tmp/qq`가 있으면 먼저 `docker exec -u root huge-app-api-1 rm -rf /tmp/qq`로 지운다. 지우지 않으면 폴더 안에 폴더가 생겨 옛 스크립트가 돈다.
