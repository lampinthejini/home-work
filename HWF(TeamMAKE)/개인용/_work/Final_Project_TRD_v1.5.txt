TRD란? PRD에 적은 기능을 "어떻게 만들지" 정하는 문서다. 서버를 어떻게 나눌지, 어떤 프로그램·라이브러리를 쓸지, 데
이터를 어떻게 저장할지, 화면과 서버가 무엇을 주고받을지, AI를 어떻게 부를지, 어떻게 테스트할지를 적는다. 사용자 입장
의 규칙이 바뀌면 PRD를 먼저 고치고 TRD를 따라 고친다.
1. 개요 및 설계 원칙
1-1. 목적 및 범위
PRD v1.6의 1차 면접 자동화 전체(공고·채점 기준 정하기 → 지원·준비 → AI 면접 → 코딩테스트 → AI 채점·1차 합격 여부 결
정 → 결과 공개 → 자동 삭제)를 서버 1대(그래픽카드 메모리 6GB · 일반 메모리 58GB)에서, 외부 서비스 없이 만들기 위한 기술
기준을 정한다. 2차 면접, 외부 시스템 연동, 모바일 앱은 범위 밖이다(PRD 2-2).
1-2. 설계 원칙
원칙
어떻게 만든다
AI가 평가하고, 시스템은 결과의 유효
성을 검증한다
AI는 지원자의 답변과 평가 기준을 바탕으로 항목별 점수, 종합 평가 점수, 1차 합격 여부와 그
이유를 판단한다. 서버는 AI 응답의 데이터 형식과 값의 범위, 근거 문장이 실제 답변에 존재하는
지를 검증한다. 검증을 통과하지 못한 결과는 확정하지 않고 재시도하거나 '확인 필요' 상태로 처
리한다. 합격 여부를 서버가 별도 점수 규칙으로 재판정하지 않는다.
면접 진행 상태와 업무 규칙은 시스템
이 관리한다
AI는 질문 생성, 답변 분석, 꼬리질문 판단 및 평가를 수행한다. 면접 시작·종료, 질문 순서, 답변
제한시간, 꼬리질문 횟수, 재접속, 결과 공개 등은 서버가 정해진 규칙에 따라 관리한다. AI가 다
음 단계로 이동할지 임의로 결정하지 않으며, 허용된 상태 전이만 수행한다.
면접은 실시간으로 진행하고, 처리 결
과는 순서에 맞게 전달한다
지원자의 음성은 WebRTC로 실시간 전송하고, STT 결과는 WebSocket을 통해 자막으로 전달
한다. 음성 수신과 STT 처리를 분리해 추론 지연이 면접 연결을 불필요하게 막지 않도록 한다.
질문, 답변, 자막 및 진행 상태는 해당 면접의 순서와 연결 관계를 유지한다.
일부 기능의 실패가 전체 면접의 중단
으로 이어지지 않게 한다
질문 생성, STT, TTS, AI 평가 및 백그라운드 작업에는 실패별 처리 방법을 정의한다. 가능한 경
우 재시도하거나 질문은행·예비 질문 또는 텍스트 표시로 대체한다. 평가 결과를 안전하게 확정
할 수 없는 경우 임의의 결과를 만들지 않고 '확인 필요' 상태로 전환한다.
필요한 데이터만 수집하고 정해진 기간
만 보관한다
이력서, 음성, 답변, 코드 및 평가 결과는 서비스 기능에 필요한 범위에서 처리한다. 개인정보 접
근은 역할과 데이터 소유권에 따라 서버에서 통제한다. 원본과 파생 데이터는 각각 정해진 보관·
삭제 정책을 따르며, 외부 AI 서비스로 개인정보나 면접 데이터를 전송하지 않는다.
기능 설정과 프로그램 로직을 분리한다
동시 면접 수, 재시도 횟수, 시간 제한 및 결과 공개·삭제 관련 설정은 프로그램 코드에 고정하지
않는다. 변경 가능한 설정은 중앙에서 관리하고, 설정 변경은 적용 범위와 시점을 명확히 하며 필
요한 감사 기록을 남긴다.
검증 가능한 기준으로 구현 완료 여부
를 판단한다
주요 기능에는 요구사항과 연결되는 테스트 기준을 둔다. 면접 상태 전이, 질문 구성, AI 결과 검
증, 권한 검사, 장애 복구, 데이터 삭제 및 성능 목표를 테스트로 확인한다. 실제 실행이나 측정으
로 확인하지 않은 기능과 성능을 완료된 것으로 간주하지 않는다.
1-3. 범위 제약 (관리자 1명 기준)
1. 계정: 관리자 계정 1개로 운영한다. 회사별 계정, 회사마다 데이터를 나누는 구조(멀티테넌시)는 만들지 않는다.
2. 공고 넣기: 관리자가 직접 쓰거나, 공공 채용정보 Open API나 더미 데이터(연습용 가짜 공고 파일)로 불러온다. 회사명·회사
소개는 공고의 칸으로 둔다.

3. 그대로 지키는 것: 지원자·관리자 역할 구분, 모든 API에서 역할과 데이터 주인 확인(지원자는 다른 지원자 데이터를 못 봄), 개

요청 흐름
1. 실행: 서버 PC 한 대에서 모든 프로그램을 Docker 컨테이너에 담아 docker compose 파일 하나로 띄운다. 포트는
127.0.0.1 에만 연결해(예: 127.0.0.1:8080:3000 ) 그 PC 안의 브라우저에서만 접속할 수 있다.
2. 화면과 일반 요청: 브라우저는 frontend( http://127.0.0.1:8080 )에 접속한다. 화면에서 보내는 /api  요청은 frontend가
Next.js 주소 넘기기(rewrites)로 api에 넘긴다. 주소가 하나라서 로그인 쿠키가 그대로 쓰인다.
3. 면접 중 음성·자막: 브라우저가 api( 127.0.0.1:8000 )에 바로 붙는다. 답변 음성은 WebRTC로 실시간 전송하고, 질문·자막·
진행 상태는 WebSocket( ws://127.0.0.1:8000 )으로 주고받는다(5-2). api는 연결이 우리 화면 주소에서 왔는지(Origin 헤
더) 확인하고, 아니면 끊는다.
4. HTTPS·문지기 없음: 이 PC 안에서만 접속하므로 HTTPS 인증서와 문지기 프로그램(NGINX)을 쓰지 않는다. 브라우저는
127.0.0.1 · localhost  주소에서는 HTTPS 없이도 마이크·카메라를 열어 준다. 다른 PC에서 접속하게 바꾸면 HTTPS와
443번 포트 하나로 받는 문지기가 필요하다(11장).
5. 내부망: AI와 데이터 상자는 서버끼리만 통하는 내부망( internal: true )에만 연결한다.
6. 밖으로 나가는 연결: api는 Open API로 공고를 불러올 때만, mailer는 Gmail 메일 서버(smtp.gmail.com, 587번 포트)로
메일을 보낼 때만 나간다(11장). 개발 중에는 Mailpit(밖으로 보내지 않는 시험용 메일 서버)을 쓴다.
쓰지 않는 것: 쿠버네티스(서버 여러 대 관리 도구), 별도 모니터링 도구, 부하 테스트 도구.

백엔드가 데이터를 받고 넘기는 모양을 예시로 정한다. 실제 칸 목록은 테이블 정의서를 따른다.
공통 규칙
1. 형식 정의: 모든 요청·응답·메시지·LLM 답은 Pydantic 모델로 정의하고 JSON으로 주고받는다. 모델에 없는 칸이 오면 거절
한다( extra="forbid" ).
2. 값 규칙: id는 UUID 문자열, 시각은 한국 시간이 붙은 ISO 8601( 2026-11-03T10:00:00+09:00 ), 점수는 소수 오차를 막기 위
해 문자열( "70.15" )로 보낸다.
3. 오류 응답: 모든 오류는 {"code", "message"}  한 가지 모양으로 보낸다. 화면은 code로 안내 문구를 고른다.
4. 개인정보: 이름·연락처는 화면 응답에만 넣고, LLM 입력과 Redis 메시지에는 넣지 않는다.

5-2. 면접 실시간 통신 (WebSocket · WebRTC)
면접 중에는 연결 두 개를 계속 열어 둔다. 답변 음성은 WebRTC로, 나머지(질문, 자막, 진행 상태, 연결 확인)는 WebSocket으로 주고받는다.
답변 음성·자막 처리 흐름
1. 연결 준비: 면접 시작 때 화면과 api가 WebSocket으로 WebRTC 연결 정보( rtc_offer · rtc_answer · rtc_ice )를 주고받는
다. 같은 PC(127.0.0.1) 안이라 외부 중계 서버(STUN·TURN)는 쓰지 않는다.
2. 받기: api는 aiortc로 음성을 받아, 답변 번호를 붙인 1초 단위 조각으로 Redis 스트림(순서가 지켜지는 작업 줄)에 넣고
MinIO에 답변 음성 파일로 이어 쓴다. api는 STT를 기다리지 않는다.
3. 실시간 자막: stt는 스트림에서 조각을 꺼내 caption_interval_sec 마다 지금까지의 음성을 글자로 바꿔 임시 자막을 만든다.
그래픽카드가 바쁘면 임시 자막은 건너뛴다. 면접 진행과 최종 글자에는 영향이 없다.
4. 보내기: api가 자막을 WebSocket caption  메시지로 화면에 보낸다. 메시지마다 질문 번호·답변 번호·조각 번호가 있어, 화
면은 순서가 뒤바뀌거나 지난 질문의 자막이면 버린다.
5. 최종 글자: 답변이 끝나면 stt가 그 답변의 전체 음성을 한 번 더 글자로 바꿔 최종 글자( is_final )를 만든다. 꼬리질문 판단과
채점은 이 최종 글자만 쓴다(7-5).

5-3. 동시 면접 입장 관리
Redis에 "지금 진행 중인 면접 수"( interview:active )를 두고, 시작 요청이 오면 설정값 N과 비교해 자리가 있을 때만 1을
더한다. 두 사람이 동시에 눌러도 N을 넘지 않게 비교와 더하기를 끼어들 틈 없이 한 번에 처리한다(Redis 안에서 한 번에 실행
되는 작은 스크립트, Lua). 면접이 끝나거나 취소되면 1을 뺀다.
끊긴 면접의 자리: 장애로 '장애 중단'이 된 면접은 끊긴 뒤 disconnect_seat_hold_min (10분) 동안만 자리를 맡아 두고, 그 시
간이 지나면 1을 빼서 다른 사람이 쓰게 한다. 창 닫기·권한 끄기로 끊긴 면접은 끊긴 순간 바로 '응시 종료'가 되므로 그때 1을
뺀다(7-2). 다시 접속(이어가기)할 때는 자리를 아직 맡아 두었든 이미 돌려주었든 N을 다시 확인하지 않고 들어오게 한다(장애
를 겪은 지원자에게 유리하게). 자리를 돌려준 뒤 다시 들어온 면접은 숫자에 다시 1을 더하므로 잠깐 N을 넘을 수 있고, 그동안

7-2. 장애 판단
서버는 면접마다 화면이 마지막으로 보낸 연결 확인 신호(heartbeat) 시각을 Redis에 두고, 15초가 넘으면 그 순간 바로 아래
기준으로 판단한다. 다시 접속할 때까지 판단을 미루지 않는다.
'장애'로 판단하면 상태를 '장애 중단'으로 바꾸고 시간을 멈춘다(남은 시간 저장). 자리는 disconnect_seat_hold_min (10분)
동안만 맡아 두고, 그 뒤에는 돌려준다(5-3). '장애 아님'으로 판단하면 '장애 중단'을 거치지 않고 바로 '응시 종료'로 끝내고 자
리를 돌려준다.
판단은 끊기기 직전 기록으로 한다. 연결이 끊기기 전 30초 안에 지원자가 창을 닫은 기록( unload : beforeunload·pagehide
이벤트)이나 권한을 끈 기록이 있으면 '장애 아님', 나머지는 모두 '장애'(원인 모름 포함, 지원자에게 유리하게).

것으로 본다.

7-4. 질문 생성 절차
②~⑤는 worker가 LangGraph 그래프 하나로 돌린다. 질문 자리마다 아래 순서로 지나간다.
1. 고르기: 질문 DB에서 후보를 고른다(②).
2. 만들기: 질문 DB에서 비슷한 질문을 찾아 예시로 넣고(RAG), LangChain으로 LLM을 불러 질문을 만들거나 다듬는다(③).
3. 확인하기: 범위를 확인하고, 형식·내용이 맞는지 코드가 검사한다(④).
4. 갈림길: 통과하면 저장한다. 실패하고 다시 만들기 횟수가 남았으면 2번으로 돌아간다. 횟수를 다 썼거나 60초 제한에 걸리면
대신 쓸 질문으로 바꾼다(⑤).

4. 베낌 확인: 만든 질문이 예시 중 하나와 비슷한 정도(코사인 유사도) 0.9 이상이면 베낀 것으로 보고 실패로 센다(⑤).

⑤ 실패 처리

7-5. 답변 처리 및 꼬리질문
면접 진행 그래프 (LangGraph)
api가 지원 1건마다 그래프 하나를 돌린다. 그래프의 이름표(thread_id)는 지원 번호다.
1. 질문 내기: 다음 질문(미리 만든 기본 질문 또는 꼬리질문)을 WebSocket으로 보낸다.
2. 답변 기다리기: 그래프를 멈춰 두고(interrupt), 답변 음성이 다 올라오면 그 자리에서 다시 움직인다.
3. 글자로 바꾸기: STT로 답변을 글자로 바꾼다.
4. 꼬리질문 판단: 남은 시간이 있으면 LangChain으로 LLM을 불러 판단 재료를 받는다.
5. 갈림길: 코드가 정한다. 꼬리질문이면 1번으로, 기본 질문이 남았으면 다음 질문으로 1번, 10개를 다 했으면 코딩테스트로, 마
감·응시 취소면 끝으로 간다.
그래프가 단계를 지날 때마다 진행 상태(지금 질문 번호, 꼬리질문 수, 남은 답변 시간)를 PostgreSQL에 저장한다(LangGraph 체
크포인트). 장애로 끊겼다 다시 접속하면 같은 지원 번호로 저장된 상태를 불러와 멈춘 단계부터 이어 간다(7-2). 응시 상태(7-1)는
지금처럼 applications 테이블이 기준이고, 체크포인트는 그래프를 이어 가는 데만 쓴다.
답변 음성은 WebRTC로 실시간으로 받고, 답변 중에는 임시 자막을 보여 준다(5-2). 답변이 끝나면 faster-whisper(한국어,
소리 없는 부분 거르기)로 전체 음성을 최종 글자로 바꾼다. 실패하면 2번 다시 하고, 그래도 안 되면 장애로 처리한다.
내용 없는 답 판단: 바꾼 글자가 비었거나 '모르겠습니다' 같은 말이면 꼬리질문 없이 다음 질문으로 간다(INT-07).
시간 나눠 쓰기: 답변이 끝나고 다음 질문이 뜨기까지의 목표 시간은 설정값 next_question_target_sec 이고, 처음 값은 13-
2에서 운영 서버로 재서 정한다. 그 안에서 ① 음성을 글자로 바꾸기(STT) ② 꼬리질문 판단 ③ 꼬리질문 음성 만들기(TTS)를
차례로 한다. 기본 질문 음성은 미리 만들어 두었으므로, 꼬리질문이 없으면 ②가 끝나는 대로 다음 질문을 보낸다.
꼬리질문 판단에는 고정된 제한 시간을 따로 두지 않고, 답변마다 남은 시간 = 목표 시간 − ①에 실제로 걸린 시간 − 꼬리질문
음성에 걸리는 시간(최근 평균)을 계산해 그만큼만 준다. 서버가 바쁠 때는 판단 시간이 저절로 줄고 한가할 때는 늘어난다. 남
은 시간이 followup_min_sec 보다 짧으면 판단하지 않고 꼬리질문 없이 넘어간다.
꼬리질문 판단은 면접 중 LLM에 남은 시간을 제한으로 걸고 불러 {need 필요한지, reason_code 이유, question 꼬리질문}
JSON을 받는다. 시간을 넘기거나 형식이 틀리면 꼬리질문 없이 넘어간다. 질문당 1개, 전체 4개 제한은 서버가 센다.
꼬리질문이 나오면 CPU의 TTS로 바로 음성을 만든다. 목표 시간 안에 음성이 안 만들어지면 그 꼬리질문은 음성 없이 자막만
으로 낸다(question 메시지의 음성 주소 null, INT-01).
1번째 화면 이탈로 끊겼던 답변(7-3)은 이탈 전과 뒤에 받은 음성을 이어 붙여 한 번에 최종 글자로 바꾼다.

3. 동시 면접 수를 늘려 가며 실시간 자막이 늦지 않는 caption_interval_sec 를 찾는다. 자막 때문에 '다음 질문' 시간이 목표를
넘으면 간격을 늘린다.
4. 이력서 샘플로 OCR 쪽당 시간과 LLM 정리 시간을 재서 ocr_sec_per_page 와 resume_llm_sec 의 처음 값으로 둔다.
5. 응시 1건(질문 10개 + 꼬리질문 4개)의 채점·결정을 8B CPU로 돌려 시간을 잰다. 10분을 넘으면 6-4의 방법 B나 C로 바꾼다.
6. 결과를 이 문서 6장과 14장 설정값에 반영하고, 바뀐 내용은 TRD_변경이력에 남긴다.
