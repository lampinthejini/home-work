# 제안 C-28 — 면접 질문 만들기: 한 사람씩 · 예비 질문 유사도 · 말투·문법 다듬기

- 작성: 2026-11-19, 모의 지원 10명 실측 뒤
- 상태: **승인·구현 (2026-11-19)** — 1 한 사람씩(최대 10분, 서류 평가도 한 사람씩) · 3 다듬기 · 2 는 대안 A(0.7) · 같은 날 3 의 4B 다듬기는 효과가 없어(50문항 중 0건) 빼고 규칙만 남김. 결과는 CONFLICTS C-28

## 1. 질문 만들기를 한 사람씩 (사용자 제안, **권장**)

| 항목 | 설명 |
|---|---|
| 제안 기능 | 질문 만들기를 **한 번에 한 사람만** 한다(줄 세우기). 앞사람이 끝나야 다음 사람을 시작한다. 시간 예산(180초)은 **줄에서 기다린 시간을 빼고, 실제로 시작한 때부터** 센다 |
| 기다릴 때 안내 | 지원자가 면접 시작을 눌렀는데 아직 질문이 없으면 "질문을 준비하고 있습니다. 앞에 N명이 있어 약 M분 걸릴 수 있습니다"를 보여 주고 기다린다(M = 앞사람 수 × 최근 평균 시간). 지금처럼 정해진 시간 뒤 서둘러 예비 질문으로 채우지 않는다 |
| 제안 이유 | 동시에 하면 모두가 느려져 결국 대부분 예비 질문이 됨(19/60). 한 사람씩이면 각자 거의 다 새로 만듦(28/30) |
| 기대 효과 | 새로 만든 질문 비율이 돌아옴. 면접 중인 사람의 꼬리질문(같은 4B)도 덜 밀림 |
| 기술적 위험 | ① 질문 만들기는 지금 api 프로세스 안의 작업이라, 줄도 프로세스 안에 둔다(api 가 하나일 때만 맞음 — 지금은 하나). ② 앞사람이 오래 걸리면 뒷사람이 오래 기다림 → **최대 기다림**이 필요(권장 10분, 넘으면 지금처럼 예비 질문으로 채움). ③ 서버가 다시 켜지면 줄이 사라짐 → 켤 때 '만드는 중'인 건을 다시 줄에 넣음(지금도 'none' 으로 되돌리는 코드가 있음) |
| 영향 범위 | `question_compose.py`(scheduleCompose·ensureComposed·compose), 면접 시작 화면(대기 안내), `routers/interview.py`(앞사람 수·예상 시간), 테스트, TRD 7-4 · 기능정의서 · 화면정의서 |
| 권장 여부 | **권장** |

정해 주실 것: 최대 기다림(권장 10분), 서류 평가도 질문 만들기와 같은 줄로 묶을지(권장: 묶지 않음 — 서류 평가는 지원자가 기다리는 화면이 없음. 대신 질문 만들기가 먼저 4B 를 쓰도록 서류 평가는 한 번에 한 사람).

## 2. 예비 질문 유사도 0.8 → 0.6 (사용자 제안, **그대로는 비권장**)

실측(BGE-M3, 지금 질문 DB):

| 기준 | 이번에 쌓인 9개 중 들어가는 수 | 지금 예비 질문 중 "가장 가까운 다른 질문"이 기준보다 낮은 비율 |
|---|---|---|
| 0.8 (지금) | 9 | 인성 15/15 · 회사 23/25 · 직무 39/43 · 이력서 10/10 |
| 0.7 | 4 | 인성 9/15 · 회사 2/25 · 직무 22/43 · 이력서 6/10 |
| **0.6** | **0** | 인성 0/15 · 회사 0/25 · 직무 7/43 · 이력서 3/10 |

- 한국어 면접 질문끼리는 주제가 달라도 유사도가 0.6 안팎이 나온다(C-19: 기본 회사 질문끼리 평균 0.61). **0.6 이면 예비 질문이 사실상 더 쌓이지 않는다.** 지금 있는 인성·회사 질문도 모두 서로 0.6 이상이다.
- 반복의 실제 원인은 "들어온 질문이 비슷해서"보다 **"동시에 몰려 예비 질문을 41번 꺼내 써서"**다. 1번(한 사람씩)을 하면 꺼내 쓰는 횟수 자체가 크게 준다.

| 항목 | 설명 |
|---|---|
| 대안 A (권장) | **0.7** 로 낮춤(이번 실측으로 4/9 통과). 뜻이 같은데 표현만 다른 것("검수와 답변 생성의 차이" 류)은 대부분 0.7~0.8 사이라 걸러진다 |
| 대안 B | 0.6 은 유지하되 **같은 분야(직무 6분야 · 회사 3초점) 안에서만** 비교. 다른 분야끼리는 비교하지 않음. 정밀하지만 예비 질문에 분야 칸이 필요(DB 칸 추가) |
| 기대 효과 | 비슷한 질문이 덜 쌓이면서도 질문 DB 는 계속 자람 |
| 기술적 위험 | A: 쌓이는 속도가 절반쯤으로 줄어듦. B: DB 스키마 변경, 기존 질문 분야 채우기 |
| 영향 범위 | `rag.RESERVE_DUPLICATE_SIMILARITY` (A는 한 줄), 테스트, CONFLICTS C-19 기록, AI 아키텍처 |
| 권장 여부 | **A 권장**(0.6 은 비권장) |

## 3. 내용 검사를 통과한 뒤 말투·문법만 다듬기 (사용자 제안, **권장**)

지금 순서: 만들기 → 글 검사(찌꺼기·두 가지 묻기·말끝 등) → 4B 다시 보기(`QuestionReview`: 앞뒤·말끝 고치기, 전제가 틀리면 다시 만들기) → 저장. 다시 보기가 "내용 판단"과 "문장 고치기"를 한 번에 하다 보니, 깨진 말끝이 그대로 지나간 건이 생겼다.

| 항목 | 설명 |
|---|---|
| 제안 기능 | 내용 검사를 모두 통과한 질문만, 마지막에 **다듬기 한 번**: 말투(면접관 존댓말 '…나요?'·'…주세요'), 맞춤법, 어색한 조사·말끝, 같은 말 되풀이("Python과 파이썬")만 고친다. **뜻·묻는 것·고유명사는 바꾸지 않는다** |
| 안전장치 | ① 고친 글과 원래 글의 유사도가 0.9 미만이면(뜻이 바뀜) 원래 글로 ② 고친 글도 글 검사를 다시 통과해야 함 — 못 지나가면 그 자리는 다시 만들기 ③ 예비 질문에는 **다듬은 글**을 넣음 |
| 제안 이유 | 내용은 맞는데 문장이 어색한 질문이 면접과 예비 질문 DB 에 그대로 남음. 관리자가 손보지 않으므로 자동으로 다듬어야 함 |
| 기대 효과 | 예비 질문 DB 의 문장 품질이 쌓일수록 좋아짐(다음 질문 만들기의 예시로도 쓰이므로 더 중요) |
| 기술적 위험 | 질문 하나에 4B 호출 1번(약 1~2초) → 한 사람 약 +15초. 1번(한 사람씩)과 함께라면 감당 가능. 4B 가 뜻을 바꿀 수 있음 → 안전장치 ① |
| 영향 범위 | `question_compose.py`(저장 직전 단계), 테스트, AI 아키텍처 · 기능정의서 |
| 권장 여부 | **권장** |

## 4. 순서 제안

1 → 3 → 2(A) 순으로 하고, 하나씩 모의 지원 10명을 다시 돌려 "새로 만든 질문 비율 · 예비 질문 쌓인 수 · 어색한 문장 수"를 이번 실측과 비교한다.
