# 프로젝트 안내

## 개요
이 프로젝트는 모의면접 프로그램 만들기 프로젝트다.
그룹으로 만들고 있지만, 일단 개개인이 작성하여
작성하고, 최선의 프로그램을 만든 것을 토대로 단체 작업을 진행한다.

## 서류에 대한 설명
참고자료로 사용하는 서류와 그리고 네가 작성해야할 서류이다. 작성할 때, 세 가지를 검토해야 한다. - 미리 설계된 학습에서 어긋나지 않는지, 막상 기술기능을 구현했을 때 오류가 발생하는지, 혹은 추가로 기능이나 기술을 해야하는지에 대해서다. 
설계된 학습에서 어긋나지 않는 것은 점검이며, 기술기능을 구현했을 때 생기는 오류들은 미리 네가 문제점을 파악하고 이야기를 해라. 서류별로 모순이 발생했을 때는 어떤걸 우선적으로 처리할지 물어보고, 정확하게 처리해야만한다.
그리고 추가적으로 필요한 기능이 있다면, 추천으로 해서 어떤 기능을 추가하고 추가했을 때 장점과 리스크를 확실히 나에게 알리고, 추가할지 물어보아라.
(1) AI기술 아키텍처 - 현재 면접프로그램에 필요한 기능들을 모아서 구조화 및 도식화를 시킨 아키텍처이다. 실질적인 기술을 어떻게 구현을 해야할지에 대한 부분이 들어가 있다.
(2) AI 채용 플랫폼 Mermaid - 전체적인 플로우를 mermaid로 구현한 이미지파일들이다. 해당 부분을 참고해서 그 구조를 토대로 흘러간다고 생각해라. 
(3) AI 채용 플랫폼 코딩테스트 - 면접질문 후, 추가된 코딩테스트 시험에 관한 플로우다. 코딩테스트는 관리자가 선택해서 공고별로 넣을 수 있는 테스트이며, 관리자페이지에서 공고관리에 코딩테스트를 추가하는 토글이 만들어지며, 보는 것으로 체크가 되어 있을 때 해당 플로우를 흘러갈 수 있도록 한다.

네가 작성해야할 서류리스트이다. 하나씩 내가 요청했을 때, 이에 대한 부분을 작성할 수 있도록 한다.
(1) PRD(Product Requirements Document) - 제품 요구사항 정의서이다. 어떤 부분을 실제 기능을 넣을 때 요구할건지 venv에 넣을 버전부터 추가로 필요한 프로그램까지, 그리고 내부적으로 구현할 때, 어떤 부분을 요구사항으로 둘건지 판단해서 적는다.
제품 개요	어떤 제품을 만드는가?
개발 목적	왜 만드는가?
타깃 사용자	누가 사용하는가?
핵심 기능	어떤 기능이 필요한가?
사용자 흐름	사용자가 어떤 순서로 이용하는가?
기능 요구사항	각 기능이 어떻게 작동해야 하는가?
비기능 요구사항	성능, 보안, 안정성 등의 조건
성공 지표	제품이 성공했는지 어떻게 판단하는가?
해당부분을 토대로 만들어라.
(2) 화면정의서 - 화면구현에 필요한 정의서이다. 플로우와 PRD를 통해서 외부에서 보이는 것을 어떻게 처리할건지, 버튼은 어디에다가 배치하고, 화면은 어디에다가 비치하면 좋을지 디자인적인 측면을 고려한다. 유저가 보기 좋고, 클릭하면 바로 알아볼 수 있는 방법으로 적는다.
(3) TRD(Technical Requirements Document) - 기술 요구사항 정의서
그것을 구현하기 위해 어떤 기술적 조건과 요구사항이 필요한지에 대한 설명이 들어있어야 한다. PRD가 단순한 방침이라면, 좀 더 구체적으로 기술을 요구사항을 적어놓는 것이라고 보면 된다.
기술 개요	시스템의 기술적 목표
기술 스택	Python, FastAPI, PostgreSQL 등
시스템 아키텍처	프론트엔드·백엔드·DB 구성
데이터 설계	DB 구조, 데이터 저장 및 처리 방식
API 요구사항	시스템 간 통신 규격
기능별 기술 요구사항	각 기능에 필요한 기술과 처리 조건
비기능 요구사항	성능, 보안, 확장성, 안정성
기술적 제약사항	개발 환경, 비용, 리소스 제한

## 추가 요구사항
'공고를 자동으로 만들기' 버튼을 넣으려고 한다. 자동으로 만들 때, 몇가지 필요한 질문을 넣고,(코딩테스트가 필요한지 여부까지) 회사의 상황에 맞춰 들어가 공고를 AI가 자동으로 만들어주는 기능을 넣고자 한다.

## 제한사항
실질적으로 유저가 이용하기에 시간이 많이 걸리는 소위 과부하가 걸리거나, 해결할 수 없는 기능이 들어간다면 2가지 원칙을 따라라.
(1) 먼저 해결사항, 대체할 수 있는 좋은 방법이 있는지 검토해본다.
(2) 없다면, 이를 진행하기 어렵다고 솔직하게 말하라.

억지로 무언가를 구현할 필요는 없다. 현실적으로 움직이는 것이 훨씬 중요하다. 
다만, 이에 대한 정확한 명시와 해결책을 제시하는 것이 중요하다.

## 안드레이 카르파시(Andrej Karpathy) 행동 원칙
1. 코딩하기 전에 먼저 생각하라 (Think Before Coding)

추측하지 말라. 헷갈리는 부분을 숨기지 말라. 여러 선택지가 있다면 그 차이를 드러내라.

구현을 시작하기 전에 다음을 수행하라.

자신의 가정을 명확하게 밝힌다.
확신이 없다면 질문한다.
여러 해석이 가능하다면, 조용히 하나를 선택하지 말고 가능한 해석들을 제시한다.
더 단순한 접근법이 있다면 그것을 알려준다.
필요하다면 현재 방식에 이의를 제기한다.
무언가 명확하지 않다면 구현을 멈춘다.
무엇이 애매한지 설명하고 질문한다.

2. 단순함을 최우선으로 하라 (Simplicity First)

문제를 해결하는 데 필요한 최소한의 코드만 작성하라.

추측에 기반한 기능은 만들지 말라.

요청받지 않은 기능은 추가하지 않는다.
한 번만 사용할 코드를 위해 추상화를 만들지 않는다.
요청되지 않은 확장성이나 설정 기능을 넣지 않는다.
현실적으로 발생하지 않는 상황을 위해 과도한 예외 처리를 하지 않는다.
200줄을 작성했는데 50줄로 해결할 수 있다면 다시 작성한다.

항상 스스로에게 질문하라.

"이 코드를 본 시니어 엔지니어가 '너무 복잡하다'고 말하지 않을까?"

그렇다면 더 단순하게 만든다.

3. 필요한 부분만 정확하게 수정하라 (Surgical Changes)

정말 필요한 부분만 수정하라.

그리고 자신이 만든 흔적만 정리하라.

기존 코드를 수정할 때는 다음 원칙을 따른다.

관련 없는 코드나 주석, 포맷을 함부로 개선하지 않는다.
문제가 없는 코드를 리팩터링하지 않는다.
자신의 취향이 아니라 기존 프로젝트의 스타일을 따른다.
관련 없는 죽은 코드(dead code)를 발견했다면 알려주기만 하고 삭제하지 않는다.

자신의 변경으로 인해 사용되지 않게 된 것들은 정리한다.

자신이 만든 미사용 import, 변수, 함수는 제거한다.
기존부터 존재하던 미사용 코드는 요청받지 않는 이상 건드리지 않는다.

항상 다음 기준을 만족해야 한다.

"수정된 모든 코드 한 줄 한 줄은 사용자의 요청과 직접 연결되어 있어야 한다."

4. 목표 중심으로 실행하라 (Goal-Driven Execution)

성공 기준을 먼저 정의하고, 검증될 때까지 반복하라.

모든 작업을 검증 가능한 목표로 바꾼다.

예를 들어

"유효성 검사를 추가하라."
→ "잘못된 입력에 대한 테스트를 먼저 작성하고, 그 테스트가 통과하도록 구현한다."
"버그를 수정하라."
→ "버그를 재현하는 테스트를 먼저 작성한 뒤, 그 테스트가 통과하도록 수정한다."
"X를 리팩터링하라."
→ "리팩터링 전후 모두 테스트가 통과하는지 확인한다."

여러 단계의 작업이라면 간단한 계획을 먼저 제시한다.

작업 수행 → 검증 방법
작업 수행 → 검증 방법
작업 수행 → 검증 방법

강력한 성공 기준이 있으면 스스로 반복하며 작업을 진행할 수 있다.

반대로

"그냥 동작하게 만들어라."

같은 모호한 목표는 계속해서 추가 확인과 질문을 필요로 하게 된다.
