## v1.2 → v1.3 변경 요약

PRD v1.3과 TRD v1.0의 결정을 반영했다. 화면 번호 체계(A1~A11, B1~B11)는 유지하고, 공통 컴포넌트 2개(사이트 내 알림, 마스코트 일러스트)를 추가했다.

1. **동시 응시 상한 안내(A6, A11)**: "면접 시작하기"를 눌렀을 때 동시 면접 수가 상한을 넘으면 **"이미 많은 면접자들이 면접 중입니다. 추후 다시 요청해주세요."** 모달을 띄우고 면접을 시작하지 않는다. 마이페이지 카드에 "면접 시작하기" 버튼을 두어 나중에 다시 시도할 수 있게 했다. 예상 대기 시간 표시 영역은 후속 버전용으로 자리만 정의했다(PRD v1.3 §6.3).
2. **강제 종료 상태값 확정(A7, A8, A11, B6)**: 화면 이탈 강제 종료는 `TERMINATED`(`endReason=FOCUS_LOSS`)로 확정했다. 답한 문항만 평가하고 안 답한 문항은 0점이며, 결과에 "강제 종료로 일부 문항만 평가되었습니다"를 표시한다(PRD v1.3 §6.3, §6.5).
3. **코딩테스트 공개 범위 2단계화(A5, A9, A10, A11, B6)**: 응시 중 "실행" 결과는 **정상 작동/비정상 작동**(실행 오류 여부) + 실행 출력·오류 메시지, 제출 후 최종 결과는 **"테스트 정답을 맞히셨습니다 / 맞히지 못했습니다"**로 표시한다(PRD v1.3 §6.4, §6.5).
4. **사이트 내 알림(공통, A11)**: 지원자 GNB에 알림 아이콘(벨)과 읽지 않은 개수 뱃지를 추가했다. 평가 완료는 메일이 아닌 이 알림으로만 알린다(PRD v1.3 §6.7).
5. **공고 자동 생성 차별 표현 경고(B4)**: 3단계 미리보기에서 차별 소지 표현에 밑줄 + 경고 툴팁을 표시하고, 상단에 경고 개수 요약을 보여준다. 게시는 막지 않는다(PRD v1.3 §10.2).
6. **면접 문항 단위(A7, A11, B6)**: 문항 수는 기본 10문항 기준으로 센다. 꼬리질문은 해당 기본 문항에 포함되어 번호를 늘리지 않는다(진행 표시 "3 / 10", 강제 종료 안내 "10문항 중 N문항", TRD D10).
6. **브랜드 자산 적용(공통, A1, A8, A10, A11, B4)**: `brand/`의 실제 로고·파비콘을 쓰고, Huge 마스코트 6단계 일러스트를 대기·완료·빈 화면에 배치했다.

## 공통 디자인 규칙(제안)

- **1차 행동(Primary CTA)**: 화면 우측 상단 또는 하단 우측에 배치, 여러 버튼 중 가장 중요한 것만 강조색(채움)으로 구분한다.
- **되돌아가기/취소**: 항상 화면 좌측(상단 좌측 또는 하단 좌측)에 배치한다.
- **상태 뱃지**: 색상만으로 구분하지 않고 텍스트 라벨을 항상 동반한다.
- **진행형 작업(저장중/제출중/연결중)**: 상단 고정 배너 또는 버튼 내부 스피너로 표시하고 중복 클릭을 막는다.
- **지원자 화면 상단 GNB**: 좌측 **Huge 로고**(워드마크, 클릭 시 A1), 우측에 로그인 상태에 따라 "로그인/회원가입" 또는 **[알림 벨(C1)] + "마이페이지"** 버튼(v1.3: 로그인 시 알림 벨 추가).
- **관리자 화면**: 좌측 고정 사이드바 상단에 **Huge 로고**, 그 아래 내비게이션 + 상단바 조직명/계정 메뉴로 지원자 화면과 명확히 구분한다.
- **푸터(v1.3)**: 모든 화면 하단에 작은 AIIT 워드마크 + "Made by AIIT".
- **체크박스 vs 토글(v1.2)**: 단순 포함/제외를 결정하는 설정(예: 코딩테스트 포함 여부)은 체크박스로 통일한다. 다단계 상태 전환이 필요한 경우에만 토글을 쓴다(현재 화면 범위에는 없음).

## 공통 컴포넌트 C1. 사이트 내 알림 (v1.3 신규)

**1. 설계 대상**: 지원자 GNB 우측의 알림 벨과 드롭다운 목록.

**2. 목적**: 평가 완료를 메일 대신 사이트 안에서 알린다(PRD v1.3 §6.5, §6.7). 지원자가 마이페이지를 계속 새로고침하지 않아도 되게 한다.

**3. 주요 UI 구성 요소**
- GNB "마이페이지" 버튼 왼쪽에 벨 아이콘. 읽지 않은 알림이 있으면 우측 상단에 숫자 뱃지(1~9, 10개 이상은 "9+")
- 벨 클릭 → 아래로 펼쳐지는 드롭다운(너비 약 360px, 최대 높이 약 400px 스크롤)
  - 상단: "알림" 제목, 우측 "모두 읽음" 텍스트 버튼
  - 항목: 아이콘 + 한 줄 제목 + 공고명 + 상대 시간("3분 전"). 읽지 않은 항목은 왼쪽 파란 점 + 연한 배경
  - 비어 있을 때: "새 알림이 없습니다"
- 알림 종류(MVP)
  - "면접 평가가 완료되었습니다. 점수와 AI 피드백을 확인하세요."
  - "코딩테스트 채점이 완료되었습니다. 결과를 확인하세요."
  - "최종 결과가 등록되었습니다."

**4. 사용자 동선 및 상호작용**
- 항목 클릭 → 읽음 처리 → A11의 해당 공고 카드 상세로 이동
- 드롭다운 밖을 클릭하거나 ESC를 누르면 닫힘

**5. 반응형 및 접근성**
- 모바일: 드롭다운 대신 전체 화면 시트
- 벨 버튼 `aria-label="알림, 읽지 않음 N개"`, 새 알림이 오면 스크린리더에 알림(aria-live="polite")

**6. 프론트엔드 구현 시 참고사항**
- `GET /me/notifications?unreadOnly=true`를 60초마다, 그리고 화면 이동 시 호출(실시간 연결은 쓰지 않음). `POST /me/notifications/{id}/read`, `POST /me/notifications/read-all`
- 메일 알림(리마인더, 일정 통보)은 기존대로 메일로 가고, 이 목록에는 나오지 않는다(MVP)

## A1. 공개 공고 목록

**1. 설계 대상 화면**: 비로그인 사용자도 접근 가능한 채용공고 목록(첫 화면).

**2. 화면의 목적**: 지원자가 직무를 탐색·검색해 관심 공고의 상세로 이동하도록 한다. PRD §6.2, Mermaid 01/02.

**3. 주요 UI 구성 요소**
- 상단 GNB: 좌측 로고, 중앙 또는 좌측 검색창(직무 키워드), 우측 "로그인" 버튼(비로그인 시) / "마이페이지"(로그인 시)
- 좌측 필터 패널: 직무 카테고리 체크박스(필수), 검색어 입력과 연동
- 메인 영역: 공고 카드 그리드(제목, 회사/부서, 코딩테스트 포함 여부 아이콘, 마감일, 상태)
- 검색 결과 없음(v1.3): 중앙에 마스코트 `02-analysis`(C2) + "조건에 맞는 공고가 없습니다" + "필터 초기화" 버튼
- 하단: 페이지네이션

**4. 사용자 동선 및 상호작용**
- 검색/필터 변경 → 목록 비동기 갱신(로딩 스피너) → 카드 클릭 → A2 공고 상세
- 상단 "로그인" 클릭 → A3 모달(진입경로=상단로그인, 성공 시 본 화면으로 복귀)
- "마이페이지" 클릭 시 로그인 상태면 A11, 아니면 A3 모달(진입경로=마이페이지 요청)

**5. 반응형 및 접근성**
- 데스크톱: 좌측 필터 + 3열 카드 그리드. 태블릿: 2열, 필터는 상단 아코디언. 모바일: 1열, 필터는 "필터" 버튼 → 바텀시트
- 카드 전체가 포커스 가능한 링크여야 하며 키보드 탭 순서는 검색→필터→카드 순

**6. 프론트엔드 구현 시 참고사항**
- `GET /jobs` 쿼리파라미터로 필터/검색/페이지 전달, SEO 고려 시 SSR 권장
- 로그인 상태·역할에 따른 GNB 버튼 분기는 클라이언트에서 UI만 바꾸고, 실제 권한 검증은 서버가 수행(PRD §7.2)

## A3. 로그인·회원가입 모달

**1. 설계 대상 화면**: 인증 모달(지원자 로그인/회원가입 + 관리자 로그인 공용).

**2. 화면의 목적**: 인증 후 진입 경로와 역할에 맞는 화면으로 복귀시킨다. PRD §6.1, Mermaid 01B.

**3. 주요 UI 구성 요소**
- 모달 중앙, 상단 "로그인/회원가입" 탭 전환, 우측 상단 닫기(X)
- 로그인 폼: 이메일, 비밀번호, 하단 "회원가입으로 전환" 링크
- 회원가입 폼: 기본 정보 + 성공 후 "이력서 등록" 또는 "건너뛰기" 선택 스텝(PRD §6.1)
- 폼 하단에 작은 안내 문구: "기업 관리자 계정은 별도 가입 없이 운영자가 발급한 아이디/비밀번호로 로그인합니다." 관리자용 별도 회원가입 UI는 제공하지 않는다.

**4. 사용자 동선 및 상호작용**
- 성공 시 역할·진입경로에 따라 복귀처 분기(Mermaid 01B 그대로 반영)
  - 지원자 + 상단 로그인 진입 → A1
  - 지원자 + 지원하기 진입 → 해당 공고 지원 절차(`jobId` 보존)
  - 지원자 + 마이페이지 요청 진입 → A11
  - **관리자 로그인 → B1 대시보드** (관리자 전용 로그인 페이지는 두지 않으며, 이 모달에서 로그인 후 역할만으로 분기한다)
- 실패 시 모달 유지, 인라인 에러 메시지(aria-live)
- 닫기(X) 클릭 시 모달 호출 전 화면으로 복귀(지원 절차 중이었다면 A2로 복귀, 강제 진행하지 않음)
- `returnTo` 검증 실패 시 **A1(공개 공고 목록)로 폴백**

**5. 반응형 및 접근성**
- 모바일: 전체 화면 시트. 포커스 트랩 적용, ESC로 닫기 가능

**6. 프론트엔드 구현 시 참고사항**
- `returnTo`는 화이트리스트 기반 내부 경로만 허용(PRD §6.1, §7.2)
- `POST /auth/login`. 관리자 계정도 동일 엔드포인트를 사용하되 서버가 role로 응답을 분기

## A6. 마이크·카메라 환경 점검

**1. 설계 대상 화면**: 면접 시작 전 장치 점검.

**2. 화면의 목적**: 마이크/카메라 권한과 품질을 사전 확인한다. PRD §6.3, Mermaid 02.

**3. 주요 UI 구성 요소**
- 중앙 카메라 프리뷰(영상)
- 프리뷰 하단 마이크 입력 레벨미터(막대 + 수치)
- 프리뷰 상단 또는 옆 장치 선택 드롭다운(카메라/마이크)
- 권한 거부 시 상단 안내 배너(브라우저 권한 재설정 가이드 링크) + "다시 시도" 버튼
- 우측 하단 "면접 시작하기" primary 버튼(점검 통과 전 비활성)
- **동시 응시 상한 안내 모달(v1.3 신규)**
  - 중앙 모달, 정보 아이콘(마스코트 사용 안 함, C2 규칙)
  - 제목: "지금은 면접을 시작할 수 없어요"
  - 본문: **"이미 많은 면접자들이 면접 중입니다. 추후 다시 요청해주세요."**
  - 보조 문구(작게): "지원 내용은 저장되었습니다. 마이페이지에서 언제든 면접을 다시 시작할 수 있습니다."
  - (후속 버전 예약 영역) 본문 아래 "예상 대기 시간: 약 N분" 한 줄 자리. **MVP에서는 표시하지 않는다**
  - 버튼: 좌측 "마이페이지로 이동"(보조), 우측 "다시 시도"(primary)

**4. 사용자 동선 및 상호작용**
- 권한 요청 → 허용 시 프리뷰/레벨미터 표시 → 거부 시 안내 + 재시도 루프
- 통과 후 "면접 시작하기" → A7
- (v1.3) "면접 시작하기"에서 상한 초과 응답을 받으면 → 상한 안내 모달
  - "다시 시도" → 같은 요청 재전송(연타 방지를 위해 버튼을 5초간 비활성화하고 남은 초를 표시)
  - "마이페이지로 이동" → A11. 카드의 "면접 시작하기" 버튼으로 나중에 A6에 다시 진입
  - 면접 세션은 `READY` 상태로 남으며, 이 거절은 응시 횟수나 평가에 영향을 주지 않는다

**5. 반응형 및 접근성**
- 레벨미터는 막대(시각)와 숫자(텍스트)를 함께 표시해 저시력 사용자도 확인 가능하게 한다
- ※ 마이크/카메라 사용이 어려운 지원자를 위한 별도 대체 응시 경로는 이번 범위에 포함하지 않는다. **향후 버전에서 장애인 대상 별도 구분 시험 트랙을 검토할 수 있다.**

**6. 프론트엔드 구현 시 참고사항**
- `getUserMedia`, HTTPS 필수, echoCancellation 권장(기술아키텍처 §5)
- (v1.3) `POST /interviews/{id}/start`가 `409 INTERVIEW_CAPACITY_FULL`을 반환하면 상한 안내 모달을 띄운다. 응답의 `estimatedWaitSec`은 MVP에서 화면에 쓰지 않는다(TRD TR-AI-23)
- (v1.3) A6 진입 시 `POST /interviews/{id}/prepare`로 기본 문항 TTS를 미리 합성한다(TRD TR-AI-12). 장치 점검 시간 동안 준비되므로 별도 로딩 UI는 두지 않는다

## A7. AI 면접 진행 화면

**1. 설계 대상 화면**: 질문 제시(텍스트+TTS) → 카운트 → 녹음 → 제출이 반복되는 면접 본 화면.

**2. 화면의 목적**: 기본 10문항(인성2/자소서2/기업2/직무4) 을 진행한다. 꼬리질문(면접 전체 최대 4개)은 해당 기본 문항에 포함된다(v1.3). PRD §6.3, Mermaid 04/05.

**3. 주요 UI 구성 요소**
- 상단 진행바: "3 / 10" 형태(기본 문항 기준, v1.3) + 현재 문항 유형 라벨(인성/자소서/기업/직무). 꼬리질문은 번호를 늘리지 않고 같은 번호에 "꼬리질문" 라벨을 덧붙인다(예: "3 / 10 · 꼬리질문")
- 중앙: 질문 텍스트 카드(크게) + TTS 재생 중 인디케이터
- TTS 종료 후 중앙 오버레이: 3-2-1 카운트
- 녹음 중 표시: 빨간 점 + 경과/제한 타이머(상단 또는 질문 카드 옆)
- 하단 우측 "제출" 버튼(녹음 중 또는 시간 만료 시 활성)
- 네트워크 중단 시 상단 고정 배너: "연결이 끊겼습니다. 마지막 저장 상태에서 재연결 중입니다"
- 화면 이탈 감지: 사용자에게 노출되는 전용 UI는 없으나, 내부적으로 Page Visibility API로 탭/창 포커스 이탈을 감지해 백그라운드 3초 타이머를 구동한다.

**4. 사용자 동선 및 상호작용**
- 질문 표시 + TTS 자동 재생(동시) → TTS 종료 → 3-2-1 카운트 → 녹음 자동 시작 → 제출/시간 만료 → 저장 중 로딩 → STT 품질 불량 시 "다시 녹음해주세요" 안내 후 재시도 → 품질 양호 시 꼬리질문 필요 여부에 따라 동일 레이아웃으로 꼬리질문 또는 다음 기본 질문 진행 → 전체 종료 시 A8(정상완료 상태)로 이동
- 사용자가 다른 탭/창으로 포커스를 이탈하면 3초 타이머 시작 → 3초 이내 복귀하면 면접 정상 진행(타이머 취소, 특별한 알림 없음) → 3초 초과하면 면접이 강제 종료(`TERMINATED`, v1.3 확정)되고, 복귀 시 A8의 강제 종료 변형 상태로 이동한다. 네트워크 중단(`INTERRUPTED`)과 별개로 취급되며 재개 대상이 아니다.
- (v1.3) 답변 제출 후 다음 질문이 나오기까지는 "다음 질문을 준비하고 있습니다" 짧은 로딩 표시를 한다. 꼬리질문 생성이 지연되어 건너뛰는 경우(TRD TR-AI-13)에도 지원자에게 따로 알리지 않고 다음 기본 질문으로 자연스럽게 넘어간다(꼬리질문은 번호를 늘리지 않으므로 진행바가 그대로 이어진다).
- **(v1.2에서도 유지)** 면접 진행 중에는 평가가 아직 산출되지 않으므로, 평가 점수·피드백은 이 화면 어디에도 노출하지 않는다(PRD §6.5). 공개 시점은 면접 종료 후 평가가 완료(`REPORT_READY`)된 뒤이며, 그 결과는 A11에서 확인한다.

**5. 반응형 및 접근성**
- 모바일: 카메라 프리뷰를 우측 상단 PIP로 축소, 질문 텍스트를 메인으로 유지
- 카운트다운은 시각(숫자)+사운드 병행, 녹음 상태는 스크린리더에 텍스트로 안내
- ※ **리스크**: 알림 확인 등 짧은 포커스 이탈도 오탐으로 면접이 종료될 수 있다. 3초라는 임계값과 오탐 허용 범위는 실제 사용 데이터로 추후 조정이 필요하다.

**6. 프론트엔드 구현 시 참고사항**
- 면접 상태값 `NOT_STARTED/READY/IN_PROGRESS/INTERRUPTED/SUBMITTED/TERMINATED/REPORT_PENDING/REPORT_READY/FAILED`(PRD v1.3 §6.3)를 화면 분기에 사용
- `INTERRUPTED`(네트워크 중단) 재진입 시 마지막 저장 상태에서 이어서 진행(PRD §7.3). 답변 도중 끊긴 문항은 처음부터 다시 출제한다(TRD TR-IV-41)
- **(v1.3 확정)** 화면 이탈 강제 종료는 신규 상태 `TERMINATED` + `endReason=FOCUS_LOSS`로 기록한다. 화면이 숨겨지는 즉시 `navigator.sendBeacon`으로 `HIDDEN` 이벤트를 보내고, 3초 초과 시 `POST /interviews/{id}/terminate`를 호출한다(TRD TR-IV-50~52)
- 답변 음성은 약 10초 단위로 잘라 말하는 동안 업로드한다(`.../segments`). 제출 후 대기 시간을 줄이기 위한 것이며 화면에는 드러나지 않는다(TRD TR-IV-20)

## A8. 면접 완료 및 다음 단계 안내

**1. 설계 대상 화면**: 면접 종료 직후 안내 화면. **정상 완료**와 **강제 종료(화면 이탈 감지)** 두 가지 상태를 표시한다.

**2. 화면의 목적**: 면접 종료를 알리고, 정상 완료 시 공고의 코딩테스트 체크 여부에 따라 다음 단계로 안내한다. 강제 종료 시에는 다음 단계로 진행하지 않고 상황을 안내한다. PRD v1.3 §5.1, §6.5.

**3. 주요 UI 구성 요소**
- **정상 완료 상태**
  - 중앙 마스코트 `01-guide`(C2, v1.3) + "면접이 완료되었습니다" 메시지
  - **안내 텍스트(v1.3 변경)**: "평가가 완료되면 상단 알림으로 알려드려요. 마이페이지에서 점수와 AI 피드백을 확인할 수 있습니다" (평가는 비동기로 처리되므로 이 화면에서 즉시 점수를 보여주지는 않는다)
  - 코딩테스트 체크된 공고: 중앙 하단 "코딩테스트로 이동" primary 버튼(단일 버튼)
  - 코딩테스트 체크 안 된 공고: 중앙 하단 "마이페이지로 이동" primary 버튼(단일 버튼)
- **강제 종료 상태**
  - 중앙 경고 아이콘 + "면접이 자동 종료되었습니다 (화면 이탈 감지)" 메시지
  - 설명 텍스트: "면접 중 다른 화면으로 3초 이상 이동하여 자동 종료되었습니다"
  - **안내 텍스트(v1.3 추가)**: "답변하신 문항까지만 평가되며, 답하지 않은 문항은 0점 처리됩니다. 평가가 완료되면 마이페이지에서 확인할 수 있습니다"
  - 코딩테스트 체크 여부와 무관하게 "마이페이지로 이동" 버튼만 노출(코딩테스트 단계로 진행하지 않음)
  - 마스코트는 쓰지 않고 경고 아이콘을 유지한다(C2 규칙)

**4. 사용자 동선 및 상호작용**
- A7에서 정상 종료 시 정상 완료 상태로 진입 → 코딩테스트 체크 ON → A9, 체크 OFF → A11
- A7에서 포커스 이탈 3초 초과 감지 시, 복귀한 시점에 강제 종료 상태로 이 화면에 진입 → "마이페이지로 이동" → A11(코딩테스트 단계 건너뜀)

**5. 반응형 및 접근성**
- 두 상태는 아이콘·문구·색조를 다르게 구분하되 텍스트로도 명확히 전달(아이콘만으로 전달하지 않음)

**6. 프론트엔드 구현 시 참고사항**
- `GET /interviews/{id}/status`로 상태 확인 후 진입. 응답의 `endReason`으로 분기한다: `COMPLETED` → 정상 완료, `FOCUS_LOSS` → 강제 종료(v1.3 확정). 평가가 진행되어 상태가 `REPORT_PENDING/REPORT_READY`로 바뀌어도 `endReason`은 유지된다
- 강제 종료 케이스는 마이페이지(A11)의 "이어서 진행" 모달 대상에서 제외해야 한다
- 이 화면은 점수·피드백을 직접 보여주지 않는다. 평가가 끝나면(`REPORT_READY`) **사이트 내 알림(C1)**으로 알리고 A11에서 공개한다(v1.3 확정, 메일 발송 없음)

## A9. 코딩테스트 메인 화면

**1. 설계 대상 화면**: 코드 작성 + 온프레미스 LLM 채팅 + 제출이 이루어지는 본 화면. (공고별 체크박스가 체크되어 있고 면접이 정상 완료된 경우에만 진입)

**2. 화면의 목적**: 문제 해결과 LLM 활용 과정을 함께 기록·평가 가능하게 한다. PRD §6.4, 코딩테스트 v0.6, 기술아키텍처 §7.

**3. 주요 UI 구성 요소**
- 최상단 바: 좌측 남은 시간 타이머, 중앙 자동저장 상태("자동저장됨 HH:MM"), 우측 남은 시험 토큰 표시(아이콘+숫자), 우측 끝 "제출" primary 버튼
- 좌측 패널(탭: 문제/실행결과): 문제 설명, 제약 조건
  - **실행결과 탭(v1.3 변경 — 중간 체크)**: 실행할 때마다 맨 위에 결과 카드 추가
    - 상태 뱃지: **"정상 작동"**(초록 + 체크 아이콘) / **"비정상 작동"**(빨강 + 경고 아이콘) — 실행 오류(문법 오류, 예외, 시간 초과, 메모리 초과) 여부만 판정
    - 비정상일 때 오류 종류를 한 줄로 표시(예: "IndexError: list index out of range", "시간 초과(5초)")
    - 실행 출력(stdout)과 오류 메시지(stderr) 접이식 영역 — 디버깅용
    - **정답 일치 여부는 표시하지 않는다.** 결과 카드 하단에 작은 안내: "실행 확인은 오류 여부만 판정합니다. 정답 여부는 제출 후 확인할 수 있습니다"
- 중앙: Monaco 코드 에디터(상단에 언어 표시, "실행" 버튼)
- 우측 패널: 온프레미스 LLM 채팅
  - 상단에 "남은 시험 토큰", "반려 가능 사유", "감점 정책", "이의제기 방법"을 안내하는 작은 정보 아이콘/링크
  - 대화 기록(스크롤), 각 LLM 응답 옆 "복사" / "에디터에 삽입" 버튼
  - 하단 프롬프트 입력창 + 전송 버튼
  - 응답 대기 중: "응답 생성 중입니다. 동시 요청이 많으면 지연될 수 있습니다" 로딩 인디케이터(기술아키텍처 §13)
  - 반려/보완요청 시: 채팅 흐름 안에 구분된 카드로 사유 · 차감량 · 재질문 가이드 표시(코딩테스트 v0.6)

**4. 사용자 동선 및 상호작용**
- 코드 작성 또는 LLM 질문(자유 선택, 반복 가능) → 실행(공개 예제 입력으로 실행, 정상/비정상 작동 판정) → 결과 확인 → 반복 → "제출" 클릭 → 확인 모달("제출 후 수정할 수 없습니다. 계속하시겠습니까?") → 확정 → A10
- LLM 질문은 허용/보완요청/반려로 분류되며, 반려 시에도 코드 편집·실행·제출은 계속 허용(PRD §6.4)
- 시험 토큰 소진 시에도 LLM 채팅 입력창은 비활성화하되 코드 편집·실행·제출은 계속 가능함을 화면에 명시

**5. 반응형 및 접근성**
- 코드 작성은 PC 환경을 기본 전제로 하며, 3단 레이아웃의 모바일 최적화는 범위 밖으로 제안한다
- 에디터 폰트 크기 조절 옵션 제공, 타이머/토큰 표시는 색상+텍스트 병행

**6. 프론트엔드 구현 시 참고사항**
- `POST /coding/sessions/{id}/llm-requests`, `POST /coding/sessions/{id}/runs`, `POST /coding/sessions/{id}/submit`, `GET /coding/sessions/{id}/token-balance`
- 네트워크 중단 시 면접과 동일하게 마지막 저장 상태(코드 스냅샷)에서 재개(PRD §7.3)
- 실제 정답·비공개 테스트는 어떤 경로로도 클라이언트에 노출하지 않는다(PRD §6.4). 이는 지원자 결과 공개 범위와는 별개로, 테스트 케이스·정답 자체를 LLM/클라이언트에 노출하지 않는다는 보안 요구사항이다
- (v1.3) `GET /coding/runs/{runId}` 응답은 `runHealth`(`NORMAL`/`ABNORMAL`), `errorType`, `stdout`, `stderr`만 포함하고 기대 출력·일치 여부 필드는 없다(TRD TR-CT-42)

## A10. 코딩테스트 제출 완료 화면

**1. 설계 대상 화면**: 코딩테스트 제출 직후 안내 화면.

**2. 화면의 목적**: 제출이 확정되었음을 알리고 마이페이지로 안내한다.

**3. 주요 UI 구성 요소**
- 중앙 마스코트 `05-report`(C2, v1.3) + 완료 메시지, 제출 시각(참고용, 작게 표시)
- **안내 문구(v1.3 변경)**: "채점이 완료되면 상단 알림으로 알려드려요. 마이페이지에서 정답 일치 여부를 확인할 수 있으며, 세부 평가는 공개되지 않습니다"
- 중앙 하단 "마이페이지로 이동" primary 버튼(단일 버튼)

**4. 사용자 동선 및 상호작용**
- 버튼 클릭 → A11

**5. 반응형 및 접근성**
- 단순 안내 화면, 완료 상태를 텍스트로 명확히 전달

**6. 프론트엔드 구현 시 참고사항**
- 제출 스냅샷은 변경 불가(PRD §6.4)로 확정된 뒤 이 화면에 진입
- 정답 일치 여부는 비동기 채점(전체 테스트 실행) 완료 후 확정되므로, 이 화면 시점에는 아직 결과가 없다. 채점이 끝나면 사이트 내 알림(C1)이 오고 A11에서 확인한다

## A11. 마이페이지

**1. 설계 대상 화면**: 지원 현황, 평가 결과(공개 범위 내), 일정 확인 화면. 지원자가 로그인 후 접근하는 유일한 상태/결과 조회처.

**2. 화면의 목적(v1.3 변경)**: "진행중/완료" 상태, **면접 평가(점수+AI 피드백)**, **코딩테스트 정답 일치 여부**, 최종 합격·불합격·보류 통지를 제공한다. 코딩테스트 세부 점수·근거와 신뢰도/검토 필요 표시는 여기에서도 노출하지 않는다(관리자 전용, PRD §6.5, §7.2). 또한 중단된 세션을 이어서 진행할 수 있도록 안내한다.

**3. 주요 UI 구성 요소**
- 세션 재개 확인 모달: 마이페이지 진입 시 INTERRUPTED 상태의 면접 또는 코딩테스트 세션이 있으면 본문 렌더와 함께(또는 그 위에 오버레이로) 확인 모달을 띄운다.
  - 문구: "진행 중이던 [면접/코딩테스트]가 있습니다. 이어서 진행하시겠습니까?"
  - 버튼: 좌측 "아니오"(보조), 우측 "예"(primary)
- 상단 GNB 공통, 상단 탭 "지원현황" / "일정"
- 지원현황 탭: 공고별 카드 목록(공고명, 지원일, 상태뱃지 — 예: 접수완료/면접대기/면접진행중/면접완료/강제종료/코딩테스트진행중/완료/결과대기/합격/불합격/보류/중단됨)
  - **(v1.3) 면접을 아직 시작하지 않은 카드**(`NOT_STARTED`/`READY`, 예: 동시 응시 상한으로 시작하지 못한 경우)에는 카드 우측에 "면접 시작하기" primary 버튼 → A6
- 지원 내역이 없을 때(v1.3): 중앙에 마스코트 `04-discovery`(C2) + "아직 지원한 공고가 없어요" + "공고 둘러보기" 버튼 → A1
- **카드 상세보기(v1.3 변경)**: 카드 클릭 시 아래 구성으로 상세를 보여준다.
  - 진행 단계 스텝퍼(지원→이력서→면접→코딩테스트→결과)
  - **"면접 평가" 섹션** — 면접 상태가 `REPORT_READY`일 때만 노출: 항목별 점수와 총점, AI 피드백 — 강점 목록, 개선점 목록. (근거 인용 원문, 신뢰도/검토 필요 표시는 **노출하지 않음**)
    - **강제 종료 면접(v1.3)**: 섹션 상단에 회색 안내 박스 "강제 종료로 10문항 중 N문항만 평가되었습니다. 답하지 않은 문항은 0점으로 반영되었습니다." 총점은 0점 반영값을 그대로 보여준다
  - **"코딩테스트 결과" 섹션(v1.3 변경)** — 채점이 끝났을 때만 노출: **"테스트 정답을 맞히셨습니다"**(체크 아이콘) 또는 **"테스트 정답을 맞히지 못했습니다"**(X 아이콘) 한 줄만 표시. (통과 테스트 개수, 세부 점수 5항목, 근거, LLM 반려 이력 등은 **노출하지 않음**)
  - **"최종 결과" 섹션** — 합격/불합격/보류 통지(결정 전에는 "심사 중")
- 일정 탭: 면접/코딩테스트 관련 일정 리스트 또는 간단 캘린더, 통보 메일의 수락·조율 링크와 연동된 항목 표시

**4. 사용자 동선 및 상호작용**
- 마이페이지 진입 → INTERRUPTED 세션 존재 시 재개 확인 모달 표시
  - [예] → 해당 세션 화면(면접이면 A7, 코딩테스트면 A9)으로 이동, 마지막 저장 지점부터 이어서 진행
  - [아니오] → 모달만 닫고 마이페이지 기본 화면 유지. 세션은 계속 INTERRUPTED 상태로 남아 다음에 마이페이지에 재진입할 때마다 동일한 모달이 다시 표시된다
- 카드 클릭 → 단계 스텝퍼 + (해당 시점까지 공개 가능한) 면접 평가 / 코딩테스트 결과 / 최종 결과 섹션을 조건부로 표시. 아직 평가가 끝나지 않은 항목은 "평가 진행 중" 등으로 표시하고 점수·결과 영역은 비워둔다

**5. 반응형 및 접근성**
- 상태 뱃지는 색상+텍스트 병행
- 모바일: 카드 1열, 탭은 상단 고정
- 재개 확인 모달은 포커스 트랩을 적용하고 기본 포커스는 "아니오"(안전한 선택)에 둔다

**6. 프론트엔드 구현 시 참고사항**
- `GET /me/applications` 및 `GET /me/applications/{id}/evaluation-summary`(TRD v1.0에서 명칭 확정)
- **(v1.3)** 지원자용 응답은 "면접 점수 + AI 피드백(강점/개선점) + `isPartial` + 코딩테스트 `codingResult`(`CORRECT`/`INCORRECT`/`PENDING`)"까지만 포함한다. **코딩테스트 세부 점수·통과 개수·근거·신뢰도/검토 필요 표시는 응답 스키마에 필드 자체가 없다**(PRD §7.2, TRD TR-SEC-10). 지원자용과 관리자용 응답 스키마는 분리되어 있다
- 사이트 내 알림 항목을 클릭해 들어온 경우 해당 카드 상세를 바로 펼친다(C1)
- A7의 화면 이탈 강제 종료 상태는 INTERRUPTED가 아니므로 이 재개 모달의 대상에서 제외한다

## B4. 공고 자동 생성

**1. 설계 대상 화면**: 질문 응답(v1.2: 선택형 + 단답형 혼합) → AI 초안 생성 → **미리보기(검토)** → (선택적 편집) → 게시로 이어지는 전용 화면(단계형).

**2. 화면의 목적**: 비전문 관리자도 빠르게 공고를 작성하되, 서술 부담을 줄이고 실제 게시될 모습 그대로 검토하도록 유도한다. PRD v1.3 §6.8, §10.

**3. 주요 UI 구성 요소**
- 상단 스텝 인디케이터: 1.질문 입력 → 2.AI 생성 중 → 3.미리보기/검토 → 4.게시
- **1단계(v1.2 전면 재설계) — 선택형 + 단답형 혼합 폼**
  - 선택형
    - 직무: 드롭다운 선택
    - 경력 연차: 칩/버튼 선택(신입 / 1~3년 / 3~5년 / 5년이상)
    - 고용 형태: 드롭다운 선택(정규직/계약직/인턴 등)
    - 코딩테스트 필요 여부: **체크박스**(v1.2 변경, 기존 라디오/토글 대체)
  - 단답형(짧은 한두 줄 입력창, placeholder로 예시 문구 제공 — 긴 자유 서술 유도 금지)
    - 회사 상황: 입력창(placeholder 예: "예: 최근 시리즈B 투자 유치")
    - 필요 역량 키워드: 태그/칩 입력 또는 쉼표 구분 짧은 입력(placeholder 예: "예: Python, 백엔드, 3년차")
  - 하단 우측 "AI 초안 생성" primary 버튼
- **2단계(v1.3 변경)**: 중앙 마스코트 `03-evaluation`(C2) + "AI가 공고 초안을 작성하고 있습니다..." + 생성되는 섹션(제목 → 설명 → 자격요건 …)을 아래에 순서대로 흘려 보여준다(스트리밍). 25~40초 걸릴 수 있으므로 진행 표시를 멈추지 않는다
- **3단계**: 지원자에게 보일 공고 상세(A2)와 동일한 레이아웃으로 AI 생성 결과를 렌더링하는 미리보기 화면. 화면 상단 우측에 "편집하기" 버튼(보조)과 "검토하기" 버튼(primary)을 둔다.
  - **차별 표현 주의 표시(v1.3 신규)**
    - 미리보기 상단(제목 위)에 노란 경고 배너: "⚠ 차별 소지가 있는 표현 N건이 있습니다. 밑줄 친 부분을 확인해주세요." (0건이면 배너 없음)
    - 해당 표현에 **노란 물결 밑줄**. 마우스를 올리거나 키보드 포커스를 주면 툴팁: 분류(연령/성별/혼인/출신 지역/신체 조건 등) + 이유 + 대체 표현 예시
      - 예: "만 30세 이하" → "연령 제한 표현은 고용상 연령차별금지법에 저촉될 수 있습니다. 예: '경력 3년 이상'처럼 역량 기준으로 바꿔보세요"
    - 배너의 "다음 항목" 버튼으로 밑줄 위치를 차례로 이동
    - 게시를 막지 않는다. "검토하기"와 게시 버튼은 경고 여부와 관계없이 동작한다
  - "편집하기" 클릭 → B3과 동일한 편집 폼으로 전환(내용은 그대로 로드, 코딩테스트 항목도 체크박스로 표시), 수정 후 "미리보기로 돌아가기"로 다시 3단계로 복귀 가능
  - "검토하기" 클릭 → 버튼 라벨이 **"검토완료"**로 바뀌고 눌림/비활성 상태로 표시, 내부 상태 `review_confirmed = true`로 설정
- **4단계**: 상단 "게시" 버튼. `review_confirmed`가 false인 상태로 게시를 누르면 **주의 모달**("AI 생성 초안을 검토하지 않았습니다. 그대로 게시하시겠습니까?") 노출, 게시 자체는 차단하지 않는다. true면 바로 게시.

**4. 사용자 동선 및 상호작용**
- 선택형 항목 선택 + 단답형 항목 1~2줄 입력 → "AI 초안 생성" → 미리보기 확인 → (선택) 편집 → "검토하기" 클릭(`review_confirmed=true`) → 게시
- 또는 미리보기에서 편집/검토 없이 바로 게시 시도(`review_confirmed=false`) → 주의 모달 → "그대로 게시" 선택 시 게시 진행

**5. 반응형 및 접근성**
- 선택형 칩/버튼은 키보드로도 선택 가능해야 하며 선택된 상태를 색상+텍스트(또는 체크 아이콘)로 표시
- 단답형 입력창은 placeholder 예시 문구가 실제 값으로 오인되지 않도록 입력 전/후 스타일을 구분한다
- 주의 모달은 포커스를 모달 내부로 이동시키고, 기본 포커스는 "취소"(안전한 선택)에 둔다
- 차별 표현 밑줄은 색(노랑)만으로 구분하지 않고 물결 밑줄 모양 + 배너 텍스트로 함께 전달한다. 툴팁은 키보드 포커스로도 열린다

**6. 프론트엔드 구현 시 참고사항**
- 입력 질문/답변(선택형 값 + 단답형 텍스트), 생성된 초안, 모델 버전, `review_confirmed` 값을 이력으로 기록(PRD §10.2)
- 코딩테스트 필요 여부 체크박스 값은 게시될 공고의 "코딩테스트 포함" 체크박스 기본값으로 그대로 반영(PRD §10.2)
- 편집 후 재저장하면 `review_confirmed`를 false로 되돌린다(TRD TR-GEN-05 제안값). "검토완료" 버튼도 다시 "검토하기"로 바뀐다
- (v1.3) 생성 API 응답에 `sensitiveTerms: [{start, end, category, reason, suggestion}]`가 포함된다. 편집 후 미리보기로 돌아오면 서버에 다시 검사를 요청해 밑줄을 갱신한다. 경고 내역은 생성 이력에 기록된다(PRD §10.2)

## B6. 지원자 상세

**1. 설계 대상 화면**: 이력서/면접 답변/코딩테스트 결과/AI 평가 전체를 열람하는 화면. 관리자 전용. PRD §5.2, §6.5, Mermaid 03/06/11.

**2. 화면의 목적**: 관리자가 지원자의 모든 산출물과 AI 평가를 검토해 최종 결정을 준비한다.

**3. 주요 UI 구성 요소**
- 상단 바: 지원자명/연락처/지원 공고/현재 상태
- 상단 탭: [이력서] [면접 답변] [코딩테스트 결과] [AI 평가 종합]
  - 이력서 탭: 표준화된 이력서 뷰 + 원본 PDF 링크
  - 면접 답변 탭: 질문별 리스트(질문 텍스트, 답변 전사, 음성 재생 버튼, 꼬리질문은 소속 기본 문항 아래 들여쓰기로 구분), 답변별 루브릭 점수(논리성/전달력/전문성/관련성) 소표시. (v1.3) 꼬리질문이 있는 문항은 기본+꼬리 답변을 합친 문항 점수를 함께 표시
    - (v1.3) 강제 종료 면접: 상단에 "강제 종료(화면 이탈) · 10문항 중 N문항 답변" 뱃지, 총점(0점 반영)과 함께 **"답변 문항 기준 평균"**을 참고값으로 표시. 답하지 않은 문항은 회색 "미응답(0점)" 행으로 표시
    - (v1.3) 화면 이탈 이벤트 타임라인(숨김/복귀 시각과 지속시간) 접이식 영역. 부정행위 확정 근거가 아니라 참고 정보임을 문구로 명시
  - 코딩테스트 결과 탭: 최종 코드(읽기 전용 에디터), 공개/비공개 테스트 결과(통과 개수 포함), **지원자에게 공개된 값("정답 맞힘/못 맞힘")을 별도 표시(v1.3)**, 응시 중 실행 이력(정상/비정상 작동), LLM 채팅 로그(허용/보완/반려 상태 뱃지 포함), 반려 이력과 감점 후보
  - AI 평가 종합 탭: 항목별 점수, 근거 인용, 신뢰도/검토 필요 뱃지, 감점 후보 확정/조정 입력, 관리자 메모 textarea
- 하단 고정 바: "최종 채용 결정" primary 버튼 → B7

**4. 사용자 동선 및 상호작용**
- 탭 전환 → 메모 작성/저장 → 감점 후보 검토(제안값 확인 후 확정/조정) → 저장 → "최종 채용 결정" 클릭

**5. 반응형 및 접근성**
- 데스크톱 전제. 탭 구조로 정보 과부하를 줄임

**6. 프론트엔드 구현 시 참고사항**
- `GET /admin/evaluations/{id}`, `POST /admin/penalty-reviews/{id}`
- **(v1.3 변경)** 이 화면은 면접·코딩테스트의 **모든** 세부 점수·근거·신뢰도/검토 필요 표시를 노출하는 유일한 화면이다. 지원자 화면(A11)에는 **면접 점수/AI 피드백 요약과 코딩테스트 정답 일치 여부까지만 노출되고, 코딩테스트 세부 평가·통과 개수와 평가 근거 원문·신뢰도 표시는 노출하지 않는다**(PRD v1.3 §7.2). 즉 "관리자 전용"의 범위가 v1.1의 "평가 전체"에서 v1.2의 "면접 세부 근거 + 코딩테스트 세부 평가 전체"로 좁아졌으므로, 관리자용 API 응답 범위와 지원자용 API 응답 범위를 분리 설계해야 한다

## B7. 최종 채용 결정

**1. 설계 대상 화면**: 합격/불합격/보류 결정 및 통지. PRD §6.5, Mermaid 06.

## B9. 평가 가중치 설정

**1. 설계 대상 화면**: 공고 단위 면접/코딩테스트 평가 항목 가중치 설정. PRD §6.5, §6.6.

**2. 화면의 목적**: 면접 루브릭(논리성/전달력/전문성/관련성)과 코딩테스트 항목(정확성/코드품질/검증·디버깅/프롬프트·AI활용판단/설명·근거)의 가중치를 공고별로 설정한다.

**3. 주요 UI 구성 요소**
- 상단: 공고 선택
- 면접 루브릭 4항목: 각각 슬라이더 + 숫자 입력, 합계 100% 실시간 검증 표시
- 코딩테스트 5항목(기본값 40/20/20/15/5): 동일한 슬라이더 + 숫자 입력 구성
- 하단 "저장" 버튼(합계가 100이 아니면 비활성 + 에러 메시지)

**4. 사용자 동선 및 상호작용**
- 값 조정 → 합계 검증 → 저장 → 안내: "이 가중치는 새 버전으로 저장되며, 기존 진행 중 평가에는 적용되지 않습니다"(버전 고정 원칙, PRD §6.5)

**5. 반응형 및 접근성**
- 슬라이더는 숫자 입력으로도 동일하게 조작 가능해야 한다(키보드 접근성)

**6. 프론트엔드 구현 시 참고사항**
- `rubric_weights` 버전 관리(기술아키텍처 §9). 이 가중치로 산출된 세부 점수는 B6/B9에서는 전체 노출되지만 A11(지원자)에는 면접 총점/피드백 수준까지만, 코딩테스트는 정답 일치 여부까지만 반영되어야 한다(공개 범위는 API 레이어에서 분리)

## 제안 사항 처리 결과

v1.0에서 제안했던 3건에 대한 사용자 결정 결과(v1.1 기록 유지).

1. **"나중에 하기"(면접완료 후 코딩테스트 지연) — 반려.** 실제 평가로 취급되는 가상면접의 특성상 지연 옵션은 부적절하다는 판단. 대신 네트워크 중단에 대한 "이어서 진행"(A11/A7/A9)은 유지하고, 의도적 화면 이탈에는 강제 종료(A7/A8, 재개 불가)를 적용했다.
2. **장애인 대상 대체 응시 경로 — 보류.** 상세 설계는 이번 범위에서 제외하고, "향후 버전에서 장애인 대상 별도 구분 시험 트랙을 검토할 수 있다"는 각주만 A6에 남겼다.
3. **공고 자동 생성 "검토 완료" 수동 표시 — 반영.** B4의 "검토하기 → 검토완료" 토글(`review_confirmed`)로 통합 구현했다.

TRD v1.0 작성 중 추천한 4건에 대한 사용자 결정(2026-10-26, v1.3 반영).

4. **면접 대기 안내 — 축소 반영.** 대기열 화면 대신 상한 초과 시 "이미 많은 면접자들이 면접 중입니다. 추후 다시 요청해주세요." 안내(A6 모달)로 처리한다. 예상 대기 시간은 서버 계산만 하고 표시 영역은 후속 버전용으로 예약했다.
5. **평가 완료 알림 — 사이트 내 알림으로 변경 반영.** 메일 대신 GNB 알림 벨(C1)로 알린다.
