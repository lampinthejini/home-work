## v1.1 → v1.2 변경 요약

PRD v1.2 확정 내용을 반영했다. 화면 번호 체계(A1~A11, B1~B11)는 이번 버전에서 변경하지 않았다(화면 추가/삭제 없음).

1. **평가 결과 공개 범위 정정(중요 정책 변경)**: v1.1에서는 "모든 평가 결과를 지원자에게 전부 비공개"로 설계했으나 이는 과도하게 제한된 설계였다(PRD v1.2 §6.5, §7.2, §7.4).
   - **AI 모의면접 평가(점수 + AI 피드백: 강점/개선점)는 평가 완료(`REPORT_READY`) 시 지원자에게 공개**한다. 단, 평가 근거 인용 원문과 신뢰도/검토 필요 표시는 여전히 **관리자 전용**이다.
   - **코딩테스트는 "정상 작동/비정상 작동" 결과만 지원자에게 공개**한다. 세부 점수(정확성/코드품질/검증·디버깅/프롬프트판단/설명근거)와 근거는 여전히 **관리자 전용**이다.
   - 최종 합격/불합격/보류 통지는 기존과 동일하게 유지한다.
   - 영향받은 화면: A5(개인정보 동의), A8(면접 완료 안내), A10(코딩테스트 제출 완료), A11(마이페이지), B6(지원자 상세). A7(면접 진행 중 화면)은 면접 중에는 애초에 평가 결과가 존재하지 않으므로 변경하지 않았다.
2. **코딩테스트 포함 여부: 토글 → 체크박스**: B3(공고 작성·수정)의 "코딩테스트 포함" 설정과 B4(공고 자동 생성) 1단계의 "코딩테스트 필요 여부" 입력을 모두 체크박스로 변경했다(PRD v1.2 §6.4, §10.1, §10.2).
3. **공고 자동 생성(B4) 1단계 입력 방식 변경**: 기존의 자유 서술 textarea 중심 입력을 **선택형(직무/경력 연차/고용 형태 — 드롭다운·칩 선택)과 짧은 단답형(회사 상황/필요 역량 키워드 — 1~2줄, placeholder로 예시 제공)이 혼합된 폼**으로 다시 설계했다(PRD v1.2 §10.1, §10.2).

## 공통 디자인 규칙(제안)

- **1차 행동(Primary CTA)**: 화면 우측 상단 또는 하단 우측에 배치, 여러 버튼 중 가장 중요한 것만 강조색(채움)으로 구분한다.
- **되돌아가기/취소**: 항상 화면 좌측(상단 좌측 또는 하단 좌측)에 배치한다.
- **상태 뱃지**: 색상만으로 구분하지 않고 텍스트 라벨을 항상 동반한다.
- **진행형 작업(저장중/제출중/연결중)**: 상단 고정 배너 또는 버튼 내부 스피너로 표시하고 중복 클릭을 막는다.
- **지원자 화면 상단 GNB**: 좌측 로고(클릭 시 A1), 우측에 로그인 상태에 따라 "로그인/회원가입" 또는 "마이페이지" 버튼.
- **관리자 화면**: 좌측 고정 사이드바 내비게이션 + 상단바 조직명/계정 메뉴로 지원자 화면과 명확히 구분한다.
- **체크박스 vs 토글(v1.2)**: 단순 포함/제외를 결정하는 설정(예: 코딩테스트 포함 여부)은 체크박스로 통일한다. 다단계 상태 전환이 필요한 경우에만 토글을 쓴다(현재 화면 범위에는 없음).

## A1. 공개 공고 목록

**1. 설계 대상 화면**: 비로그인 사용자도 접근 가능한 채용공고 목록(첫 화면).

**2. 화면의 목적**: 지원자가 직무를 탐색·검색해 관심 공고의 상세로 이동하도록 한다. PRD §6.2, Mermaid 01/02.

**3. 주요 UI 구성 요소**
- 상단 GNB: 좌측 로고, 중앙 또는 좌측 검색창(직무 키워드), 우측 "로그인" 버튼(비로그인 시) / "마이페이지"(로그인 시)
- 좌측 필터 패널: 직무 카테고리 체크박스(필수), 검색어 입력과 연동
- 메인 영역: 공고 카드 그리드(제목, 회사/부서, 코딩테스트 포함 여부 아이콘, 마감일, 상태)
- 하단: 페이지네이션

**4. 사용자 동선 및 상호작용**
- 검색/필터 변경 → 목록 비동기 갱신(로딩 스피너) → 카드 클릭 → A2 공고 상세
- 상단 "로그인" 클릭 → A3 모달(진입경로=상단로그인, 성공 시 본 화면으로 복귀)
- "마이페이지" 클릭 시 로그인 상태면 A11, 아니면 A3 모달(진입경로=마이페이지 요청)

**5. 반응형 및 접근성**
- 데스크톱: 좌측 필터 + 3열 카드 그리드. 태블릿: 2열, 필터는 상단 아코디언. 모바일: 1열, 필터는 "필터" 버튼 → 바텀시트
- 카드 전체가 포커스 가능한 링크여야 하며 키보드 탭 순서는 검색→필터→카드 순

**6. 프론트엔드 구현 시 참고사항**
- `GET /jobs` 쿼리파라미터로 필터/검색/페이지 전달, SEO 고려 시 SSR 권장
- 로그인 상태·역할에 따른 GNB 버튼 분기는 클라이언트에서 UI만 바꾸고, 실제 권한 검증은 서버가 수행(PRD §7.2)

## A2. 공고 상세

**1. 설계 대상 화면**: 개별 채용공고 상세 페이지.

**2. 화면의 목적**: 공고 내용을 확인하고 "지원하기"로 지원 절차를 시작하도록 유도한다. PRD §6.2, Mermaid 01/02.

**3. 주요 UI 구성 요소**
- 상단 좌측 "목록으로" 링크(뒤로가기 방향성)
- 본문(좌측 약 70%): 공고 제목, 회사/부서, 근무조건, 자격요건, 우대사항, "코딩테스트 포함" 뱃지(아이콘+텍스트)
- 우측 사이드카드(스크롤 시 고정/sticky): 마감일, "지원하기" primary 버튼

**4. 사용자 동선 및 상호작용**
- "지원하기" 클릭 → 로그인 상태 분기(Mermaid 01B/02)
  - 미로그인 → A3 모달(진입경로=지원하기, `jobId` 보존)
  - 지원자 로그인됨 → 해당 공고 지원 절차(A4 또는 이력서 유무에 따라 A5)로 이동
  - 관리자 로그인됨 → "지원자 권한 필요" 안내 배너/모달 표시 후 진행 차단
  - 이미 지원한 공고면 버튼을 "지원완료 · 마이페이지에서 확인" 형태로 비활성화 표시

**5. 반응형 및 접근성**
- 모바일: 우측 사이드카드를 화면 하단 고정 바(fixed bottom bar)의 "지원하기" 버튼으로 전환
- 코딩테스트 포함 여부는 색상뿐 아니라 아이콘+텍스트로 전달(색맹 고려)

**6. 프론트엔드 구현 시 참고사항**
- `GET /jobs/{id}`. 중복 지원 여부는 클릭 시 서버 확인(PRD §6.2)

## A3. 로그인·회원가입 모달

**1. 설계 대상 화면**: 인증 모달(지원자 로그인/회원가입 + 관리자 로그인 공용).

**2. 화면의 목적**: 인증 후 진입 경로와 역할에 맞는 화면으로 복귀시킨다. PRD §6.1, Mermaid 01B.

**3. 주요 UI 구성 요소**
- 모달 중앙, 상단 "로그인/회원가입" 탭 전환, 우측 상단 닫기(X)
- 로그인 폼: 이메일, 비밀번호, 하단 "회원가입으로 전환" 링크
- 회원가입 폼: 기본 정보 + 성공 후 "이력서 등록" 또는 "건너뛰기" 선택 스텝(PRD §6.1)
- 폼 하단에 작은 안내 문구: "기업 관리자 계정은 별도 가입 없이 운영자가 발급한 아이디/비밀번호로 로그인합니다." 관리자용 별도 회원가입 UI는 제공하지 않는다.

**4. 사용자 동선 및 상호작용**
- 성공 시 역할·진입경로에 따라 복귀처 분기(Mermaid 01B 그대로 반영)
  - 지원자 + 상단 로그인 진입 → A1
  - 지원자 + 지원하기 진입 → 해당 공고 지원 절차(`jobId` 보존)
  - 지원자 + 마이페이지 요청 진입 → A11
  - **관리자 로그인 → B1 대시보드** (관리자 전용 로그인 페이지는 두지 않으며, 이 모달에서 로그인 후 역할만으로 분기한다)
- 실패 시 모달 유지, 인라인 에러 메시지(aria-live)
- 닫기(X) 클릭 시 모달 호출 전 화면으로 복귀(지원 절차 중이었다면 A2로 복귀, 강제 진행하지 않음)
- `returnTo` 검증 실패 시 **A1(공개 공고 목록)로 폴백**

**5. 반응형 및 접근성**
- 모바일: 전체 화면 시트. 포커스 트랩 적용, ESC로 닫기 가능

**6. 프론트엔드 구현 시 참고사항**
- `returnTo`는 화이트리스트 기반 내부 경로만 허용(PRD §6.1, §7.2)
- `POST /auth/login`. 관리자 계정도 동일 엔드포인트를 사용하되 서버가 role로 응답을 분기

## A4. 이력서 등록 및 확인·수정

**1. 설계 대상 화면**: PDF 업로드/직접 작성, 추출 결과 확인·정정, 기존 이력서 조회·수정.

**2. 화면의 목적**: 지원에 필요한 이력서를 등록하거나 기존 이력서를 확인·수정한다. PRD §6.2, Mermaid 02.

**3. 주요 UI 구성 요소**
- 이력서 없음: 상단에 "PDF 업로드" / "직접 작성" 선택 탭, 업로드 시 중앙 드래그앤드롭 박스
- 추출 결과 확인(업로드 후): 좌측 원본 PDF 미리보기, 우측 추출된 필드 폼(학력/경력/스킬/자기소개, 모두 수정 가능)
- 이력서 있음: 동일한 필드 폼이 읽기 모드로 표시, 우측 상단 "수정" 버튼
- 하단 우측 "확정하고 계속" primary 버튼, 좌측 "이전" 보조 버튼

**4. 사용자 동선 및 상호작용**
- 업로드/작성 → 추출 결과 확인·정정 → 확정 → A5(개인정보 동의, 이미 동의했다면 생략 가능성은 운영 시 결정)
- 기존 이력서 수정 클릭 → 편집모드 전환 → 저장

**5. 반응형 및 접근성**
- 모바일: 원본 미리보기/필드 폼 좌우 분할을 세로 스택(미리보기는 접이식 아코디언)으로 전환
- 업로드 박스는 키보드로 접근 가능한 "파일 선택" 버튼을 항상 병행 제공

**6. 프론트엔드 구현 시 참고사항**
- `POST /documents/upload-url`(서명 URL) → `POST /documents/{id}/confirm`
- PDF는 텍스트 추출 우선, 스캔 문서는 OCR(기술아키텍처 §6)

## A5. 개인정보 동의 화면

**1. 설계 대상 화면**: 지원 절차 중 개인정보 수집·이용 동의.

**2. 화면의 목적**: 데이터 수집 목적과 **평가 결과 공개 범위**를 사전 고지하고 동의를 받는다. PRD v1.2 §6.1, §7.4.

**3. 주요 UI 구성 요소**
- 상단 타이틀 "개인정보 수집·이용 동의"
- 본문 스크롤 영역(약관 전문) — 스크롤을 끝까지 하지 않아도 체크박스 활성화 가능(스크롤 강제 없음)
- **강조 고지 박스(v1.2 변경)**: 굵은 테두리/배경으로 구분
  - "AI 면접의 평가 결과(점수, AI 피드백)는 본인에게 공개됩니다."
  - "코딩테스트는 정상 작동/비정상 작동 결과만 공개되며, 세부 평가 점수와 근거는 채용담당자에게만 제공됩니다."
  - "AI가 불완전하거나 틀린 답을 줄 수 있으며, 코딩테스트에는 감점 정책이 적용됩니다."
- 하단 좌측 "취소"(공고 상세로 복귀) / 우측 "동의하고 계속" primary 버튼 + 동의 체크박스

**4. 사용자 동선 및 상호작용**
- 체크박스 미체크 시 "동의하고 계속" 비활성화
- 동의 → A4(이력서 확인, 이미 확정돼 있다면 생략) → A6

**5. 반응형 및 접근성**
- 체크박스 라벨 전체를 클릭 가능하게 구성, 강조 박스는 색상+아이콘 병행

**6. 프론트엔드 구현 시 참고사항**
- `consents` 테이블에 버전과 동의 시각 기록(PRD §7.4). 고지 문구는 동의 버전과 함께 보존해 추후 "어떤 문구에 동의했는지" 추적 가능해야 한다

## A6. 마이크·카메라 환경 점검

**1. 설계 대상 화면**: 면접 시작 전 장치 점검.

**2. 화면의 목적**: 마이크/카메라 권한과 품질을 사전 확인한다. PRD §6.3, Mermaid 02.

**3. 주요 UI 구성 요소**
- 중앙 카메라 프리뷰(영상)
- 프리뷰 하단 마이크 입력 레벨미터(막대 + 수치)
- 프리뷰 상단 또는 옆 장치 선택 드롭다운(카메라/마이크)
- 권한 거부 시 상단 안내 배너(브라우저 권한 재설정 가이드 링크) + "다시 시도" 버튼
- 우측 하단 "면접 시작하기" primary 버튼(점검 통과 전 비활성)

**4. 사용자 동선 및 상호작용**
- 권한 요청 → 허용 시 프리뷰/레벨미터 표시 → 거부 시 안내 + 재시도 루프
- 통과 후 "면접 시작하기" → A7

**5. 반응형 및 접근성**
- 레벨미터는 막대(시각)와 숫자(텍스트)를 함께 표시해 저시력 사용자도 확인 가능하게 한다
- ※ 마이크/카메라 사용이 어려운 지원자를 위한 별도 대체 응시 경로는 이번 범위에 포함하지 않는다. **향후 버전에서 장애인 대상 별도 구분 시험 트랙을 검토할 수 있다.**

**6. 프론트엔드 구현 시 참고사항**
- `getUserMedia`, HTTPS 필수, echoCancellation 권장(기술아키텍처 §5)

## A7. AI 면접 진행 화면

**1. 설계 대상 화면**: 질문 제시(텍스트+TTS) → 카운트 → 녹음 → 제출이 반복되는 면접 본 화면.

**2. 화면의 목적**: 기본 10문항(인성2/자소서2/기업2/직무4) + 꼬리질문 최대 4개(총 최대 14문항)를 진행한다. PRD §6.3, Mermaid 04/05.

**3. 주요 UI 구성 요소**
- 상단 진행바: "3 / 최대 14" 형태 + 현재 문항 유형 라벨(인성/자소서/기업/직무/꼬리질문)
- 중앙: 질문 텍스트 카드(크게) + TTS 재생 중 인디케이터
- TTS 종료 후 중앙 오버레이: 3-2-1 카운트
- 녹음 중 표시: 빨간 점 + 경과/제한 타이머(상단 또는 질문 카드 옆)
- 하단 우측 "제출" 버튼(녹음 중 또는 시간 만료 시 활성)
- 네트워크 중단 시 상단 고정 배너: "연결이 끊겼습니다. 마지막 저장 상태에서 재연결 중입니다"
- 화면 이탈 감지: 사용자에게 노출되는 전용 UI는 없으나, 내부적으로 Page Visibility API로 탭/창 포커스 이탈을 감지해 백그라운드 3초 타이머를 구동한다.

**4. 사용자 동선 및 상호작용**
- 질문 표시 + TTS 자동 재생(동시) → TTS 종료 → 3-2-1 카운트 → 녹음 자동 시작 → 제출/시간 만료 → 저장 중 로딩 → STT 품질 불량 시 "다시 녹음해주세요" 안내 후 재시도 → 품질 양호 시 꼬리질문 필요 여부에 따라 동일 레이아웃으로 꼬리질문 또는 다음 기본 질문 진행 → 전체 종료 시 A8(정상완료 상태)로 이동
- 사용자가 다른 탭/창으로 포커스를 이탈하면 3초 타이머 시작 → 3초 이내 복귀하면 면접 정상 진행(타이머 취소, 특별한 알림 없음) → 3초 초과하면 면접이 강제 종료되고, 복귀 시 A8의 강제 종료 변형 상태로 이동한다. 네트워크 중단(INTERRUPTED)과 별개로 취급되며 재개 대상이 아니다.
- **(v1.2에서도 유지)** 면접 진행 중에는 평가가 아직 산출되지 않으므로, 평가 점수·피드백은 이 화면 어디에도 노출하지 않는다(PRD §6.5). 공개 시점은 면접 종료 후 평가가 완료(`REPORT_READY`)된 뒤이며, 그 결과는 A11에서 확인한다.

**5. 반응형 및 접근성**
- 모바일: 카메라 프리뷰를 우측 상단 PIP로 축소, 질문 텍스트를 메인으로 유지
- 카운트다운은 시각(숫자)+사운드 병행, 녹음 상태는 스크린리더에 텍스트로 안내
- ※ **리스크**: 알림 확인 등 짧은 포커스 이탈도 오탐으로 면접이 종료될 수 있다. 3초라는 임계값과 오탐 허용 범위는 실제 사용 데이터로 추후 조정이 필요하다.

**6. 프론트엔드 구현 시 참고사항**
- 면접 상태값 `NOT_STARTED/READY/IN_PROGRESS/INTERRUPTED/SUBMITTED/REPORT_PENDING/REPORT_READY/FAILED`(PRD §6.3)를 화면 분기에 사용
- `INTERRUPTED`(네트워크 중단) 재진입 시 마지막 저장 상태에서 이어서 진행(PRD §7.3)
- 화면 이탈 강제 종료는 기존 상태값 중 어디에 매핑할지(예: `FAILED` 재사용 또는 신규 상태 추가) 백엔드/TRD와 별도 협의가 필요하다

## A8. 면접 완료 및 다음 단계 안내

**1. 설계 대상 화면**: 면접 종료 직후 안내 화면. **정상 완료**와 **강제 종료(화면 이탈 감지)** 두 가지 상태를 표시한다.

**2. 화면의 목적**: 면접 종료를 알리고, 정상 완료 시 공고의 코딩테스트 체크 여부에 따라 다음 단계로 안내한다. 강제 종료 시에는 다음 단계로 진행하지 않고 상황을 안내한다. PRD v1.2 §5.1, §6.5.

**3. 주요 UI 구성 요소**
- **정상 완료 상태**
  - 중앙 완료 아이콘(체크) + "면접이 완료되었습니다" 메시지
  - **안내 텍스트(v1.2 변경)**: "평가가 완료되면 마이페이지에서 점수와 AI 피드백을 확인할 수 있습니다" (평가는 비동기로 처리되므로 이 화면에서 즉시 점수를 보여주지는 않는다)
  - 코딩테스트 체크된 공고: 중앙 하단 "코딩테스트로 이동" primary 버튼(단일 버튼)
  - 코딩테스트 체크 안 된 공고: 중앙 하단 "마이페이지로 이동" primary 버튼(단일 버튼)
- **강제 종료 상태**
  - 중앙 경고 아이콘 + "면접이 자동 종료되었습니다 (화면 이탈 감지)" 메시지
  - 설명 텍스트: "면접 중 다른 화면으로 3초 이상 이동하여 자동 종료되었습니다"
  - 코딩테스트 체크 여부와 무관하게 "마이페이지로 이동" 버튼만 노출(코딩테스트 단계로 진행하지 않음)

**4. 사용자 동선 및 상호작용**
- A7에서 정상 종료 시 정상 완료 상태로 진입 → 코딩테스트 체크 ON → A9, 체크 OFF → A11
- A7에서 포커스 이탈 3초 초과 감지 시, 복귀한 시점에 강제 종료 상태로 이 화면에 진입 → "마이페이지로 이동" → A11(코딩테스트 단계 건너뜀)

**5. 반응형 및 접근성**
- 두 상태는 아이콘·문구·색조를 다르게 구분하되 텍스트로도 명확히 전달(아이콘만으로 전달하지 않음)

**6. 프론트엔드 구현 시 참고사항**
- `GET /interviews/{id}/status`로 상태 확인 후 진입(정상완료=`SUBMITTED` 이상, 강제종료=별도 상태값, A7 참조)
- 강제 종료 케이스는 마이페이지(A11)의 "이어서 진행" 모달 대상에서 제외해야 한다
- 이 화면은 점수·피드백을 직접 보여주지 않는다. 평가가 비동기로 끝난 뒤(`REPORT_READY`) A11에서 공개되므로, "평가 완료 알림"을 마이페이지/이메일 등으로 보낼지는 PRD §6.7(비동기 알림) 범위와 연계해 추후 결정한다

## A9. 코딩테스트 메인 화면

**1. 설계 대상 화면**: 코드 작성 + 온프레미스 LLM 채팅 + 제출이 이루어지는 본 화면. (공고별 체크박스가 체크되어 있고 면접이 정상 완료된 경우에만 진입)

**2. 화면의 목적**: 문제 해결과 LLM 활용 과정을 함께 기록·평가 가능하게 한다. PRD §6.4, 코딩테스트 v0.6, 기술아키텍처 §7.

**3. 주요 UI 구성 요소**
- 최상단 바: 좌측 남은 시간 타이머, 중앙 자동저장 상태("자동저장됨 HH:MM"), 우측 남은 시험 토큰 표시(아이콘+숫자), 우측 끝 "제출" primary 버튼
- 좌측 패널(탭: 문제/실행결과): 문제 설명, 제약 조건
- 중앙: Monaco 코드 에디터(상단에 언어 표시, "실행" 버튼)
- 우측 패널: 온프레미스 LLM 채팅
  - 상단에 "남은 시험 토큰", "반려 가능 사유", "감점 정책", "이의제기 방법"을 안내하는 작은 정보 아이콘/링크
  - 대화 기록(스크롤), 각 LLM 응답 옆 "복사" / "에디터에 삽입" 버튼
  - 하단 프롬프트 입력창 + 전송 버튼
  - 응답 대기 중: "응답 생성 중입니다. 동시 요청이 많으면 지연될 수 있습니다" 로딩 인디케이터(기술아키텍처 §13)
  - 반려/보완요청 시: 채팅 흐름 안에 구분된 카드로 사유 · 차감량 · 재질문 가이드 표시(코딩테스트 v0.6)

**4. 사용자 동선 및 상호작용**
- 코드 작성 또는 LLM 질문(자유 선택, 반복 가능) → 실행(공개 테스트) → 결과 확인 → 반복 → "제출" 클릭 → 확인 모달("제출 후 수정할 수 없습니다. 계속하시겠습니까?") → 확정 → A10
- LLM 질문은 허용/보완요청/반려로 분류되며, 반려 시에도 코드 편집·실행·제출은 계속 허용(PRD §6.4)
- 시험 토큰 소진 시에도 LLM 채팅 입력창은 비활성화하되 코드 편집·실행·제출은 계속 가능함을 화면에 명시

**5. 반응형 및 접근성**
- 코드 작성은 PC 환경을 기본 전제로 하며, 3단 레이아웃의 모바일 최적화는 범위 밖으로 제안한다
- 에디터 폰트 크기 조절 옵션 제공, 타이머/토큰 표시는 색상+텍스트 병행

**6. 프론트엔드 구현 시 참고사항**
- `POST /coding/sessions/{id}/llm-requests`, `POST /coding/sessions/{id}/runs`, `POST /coding/sessions/{id}/submit`, `GET /coding/sessions/{id}/token-balance`
- 네트워크 중단 시 면접과 동일하게 마지막 저장 상태(코드 스냅샷)에서 재개(PRD §7.3)
- 실제 정답·비공개 테스트는 어떤 경로로도 클라이언트에 노출하지 않는다(PRD §6.4). 이는 지원자 결과 공개 범위(정상/비정상만 공개)와는 별개로, 테스트 케이스·정답 자체를 LLM/클라이언트에 노출하지 않는다는 보안 요구사항이다

## A10. 코딩테스트 제출 완료 화면

**1. 설계 대상 화면**: 코딩테스트 제출 직후 안내 화면.

**2. 화면의 목적**: 제출이 확정되었음을 알리고 마이페이지로 안내한다.

**3. 주요 UI 구성 요소**
- 중앙 완료 메시지, 제출 시각(참고용, 작게 표시)
- **안내 문구(v1.2 변경)**: "코딩테스트는 정상 작동/비정상 작동 결과만 제공되며, 세부 평가는 공개되지 않습니다"
- 중앙 하단 "마이페이지로 이동" primary 버튼(단일 버튼)

**4. 사용자 동선 및 상호작용**
- 버튼 클릭 → A11

## A11. 마이페이지

**1. 설계 대상 화면**: 지원 현황, 평가 결과(공개 범위 내), 일정 확인 화면. 지원자가 로그인 후 접근하는 유일한 상태/결과 조회처.

**2. 화면의 목적(v1.2 변경)**: "진행중/완료" 상태, **면접 평가(점수+AI 피드백)**, **코딩테스트 정상/비정상 작동 결과**, 최종 합격·불합격·보류 통지를 제공한다. 코딩테스트 세부 점수·근거와 신뢰도/검토 필요 표시는 여기에서도 노출하지 않는다(관리자 전용, PRD §6.5, §7.2). 또한 중단된 세션을 이어서 진행할 수 있도록 안내한다.

**3. 주요 UI 구성 요소**
- 세션 재개 확인 모달: 마이페이지 진입 시 INTERRUPTED 상태의 면접 또는 코딩테스트 세션이 있으면 본문 렌더와 함께(또는 그 위에 오버레이로) 확인 모달을 띄운다.
  - 문구: "진행 중이던 [면접/코딩테스트]가 있습니다. 이어서 진행하시겠습니까?"
  - 버튼: 좌측 "아니오"(보조), 우측 "예"(primary)
- 상단 GNB 공통, 상단 탭 "지원현황" / "일정"
- 지원현황 탭: 공고별 카드 목록(공고명, 지원일, 상태뱃지 — 예: 접수완료/면접진행중/면접완료/코딩테스트진행중/완료/결과대기/합격/불합격/보류/중단됨)
- **카드 상세보기(v1.2 전면 재설계)**: 카드 클릭 시 아래 구성으로 상세를 보여준다.
  - 진행 단계 스텝퍼(지원→이력서→면접→코딩테스트→결과)
  - **"면접 평가" 섹션** — 면접 상태가 `REPORT_READY`일 때만 노출: 항목별 점수(또는 총점), AI 피드백 — 강점 목록, 개선점 목록. (근거 인용 원문, 신뢰도/검토 필요 표시는 **노출하지 않음**)
  - **"코딩테스트 결과" 섹션** — 코딩테스트가 완료되고 채점이 끝났을 때만 노출: "정상 작동" 또는 "비정상 작동" 뱃지만 표시. (세부 점수 5항목, 근거, LLM 반려 이력 등은 **노출하지 않음**)
  - **"최종 결과" 섹션** — 합격/불합격/보류 통지(결정 전에는 "심사 중")
- 일정 탭: 면접/코딩테스트 관련 일정 리스트 또는 간단 캘린더, 통보 메일의 수락·조율 링크와 연동된 항목 표시

**4. 사용자 동선 및 상호작용**
- 마이페이지 진입 → INTERRUPTED 세션 존재 시 재개 확인 모달 표시
  - [예] → 해당 세션 화면(면접이면 A7, 코딩테스트면 A9)으로 이동, 마지막 저장 지점부터 이어서 진행
  - [아니오] → 모달만 닫고 마이페이지 기본 화면 유지. 세션은 계속 INTERRUPTED 상태로 남아 다음에 마이페이지에 재진입할 때마다 동일한 모달이 다시 표시된다
- 카드 클릭 → 단계 스텝퍼 + (해당 시점까지 공개 가능한) 면접 평가 / 코딩테스트 결과 / 최종 결과 섹션을 조건부로 표시. 아직 평가가 끝나지 않은 항목은 "평가 진행 중" 등으로 표시하고 점수·결과 영역은 비워둔다

**5. 반응형 및 접근성**
- 상태 뱃지는 색상+텍스트 병행
- 모바일: 카드 1열, 탭은 상단 고정
- 재개 확인 모달은 포커스 트랩을 적용하고 기본 포커스는 "아니오"(안전한 선택)에 둔다

**6. 프론트엔드 구현 시 참고사항**
- `GET /me/applications` 및 평가 상세 조회 API(예: `GET /me/applications/{id}/evaluation-summary`, 명칭은 TRD에서 확정)
- **(v1.2 핵심)** 서버 API 응답 자체가 지원자 권한으로는 "면접 점수 + AI 피드백(강점/개선점)"까지만 포함하고, **코딩테스트 세부 점수·근거·신뢰도/검토 필요 표시는 응답에 포함하지 않도록** 설계해야 한다(PRD §7.2). 즉 지원자용 응답 스키마와 관리자용 응답 스키마를 분리하는 것을 전제로 한다
- A7의 화면 이탈 강제 종료 상태는 INTERRUPTED가 아니므로 이 재개 모달의 대상에서 제외한다

## B4. 공고 자동 생성

**1. 설계 대상 화면**: 질문 응답(v1.2: 선택형 + 단답형 혼합) → AI 초안 생성 → **미리보기(검토)** → (선택적 편집) → 게시로 이어지는 전용 화면(단계형).

**2. 화면의 목적**: 비전문 관리자도 빠르게 공고를 작성하되, 서술 부담을 줄이고 실제 게시될 모습 그대로 검토하도록 유도한다. PRD v1.2 §6.8, §10.

**3. 주요 UI 구성 요소**
- 상단 스텝 인디케이터: 1.질문 입력 → 2.AI 생성 중 → 3.미리보기/검토 → 4.게시
- **1단계(v1.2 전면 재설계) — 선택형 + 단답형 혼합 폼**
  - 선택형
    - 직무: 드롭다운 선택
    - 경력 연차: 칩/버튼 선택(신입 / 1~3년 / 3~5년 / 5년이상)
    - 고용 형태: 드롭다운 선택(정규직/계약직/인턴 등)
    - 코딩테스트 필요 여부: **체크박스**(v1.2 변경, 기존 라디오/토글 대체)
  - 단답형(짧은 한두 줄 입력창, placeholder로 예시 문구 제공 — 긴 자유 서술 유도 금지)
    - 회사 상황: 입력창(placeholder 예: "예: 최근 시리즈B 투자 유치")
    - 필요 역량 키워드: 태그/칩 입력 또는 쉼표 구분 짧은 입력(placeholder 예: "예: Python, 백엔드, 3년차")
  - 하단 우측 "AI 초안 생성" primary 버튼
- **2단계**: 중앙 로딩 상태("AI가 공고 초안을 작성하고 있습니다...")
- **3단계**: 지원자에게 보일 공고 상세(A2)와 동일한 레이아웃으로 AI 생성 결과를 렌더링하는 미리보기 화면. 화면 상단 우측에 "편집하기" 버튼(보조)과 "검토하기" 버튼(primary)을 둔다.
  - "편집하기" 클릭 → B3과 동일한 편집 폼으로 전환(내용은 그대로 로드, 코딩테스트 항목도 체크박스로 표시), 수정 후 "미리보기로 돌아가기"로 다시 3단계로 복귀 가능
  - "검토하기" 클릭 → 버튼 라벨이 **"검토완료"**로 바뀌고 눌림/비활성 상태로 표시, 내부 상태 `review_confirmed = true`로 설정
- **4단계**: 상단 "게시" 버튼. `review_confirmed`가 false인 상태로 게시를 누르면 **주의 모달**("AI 생성 초안을 검토하지 않았습니다. 그대로 게시하시겠습니까?") 노출, 게시 자체는 차단하지 않는다. true면 바로 게시.

**4. 사용자 동선 및 상호작용**
- 선택형 항목 선택 + 단답형 항목 1~2줄 입력 → "AI 초안 생성" → 미리보기 확인 → (선택) 편집 → "검토하기" 클릭(`review_confirmed=true`) → 게시
- 또는 미리보기에서 편집/검토 없이 바로 게시 시도(`review_confirmed=false`) → 주의 모달 → "그대로 게시" 선택 시 게시 진행

**5. 반응형 및 접근성**
- 선택형 칩/버튼은 키보드로도 선택 가능해야 하며 선택된 상태를 색상+텍스트(또는 체크 아이콘)로 표시
- 단답형 입력창은 placeholder 예시 문구가 실제 값으로 오인되지 않도록 입력 전/후 스타일을 구분한다
- 주의 모달은 포커스를 모달 내부로 이동시키고, 기본 포커스는 "취소"(안전한 선택)에 둔다

**6. 프론트엔드 구현 시 참고사항**
- 입력 질문/답변(선택형 값 + 단답형 텍스트), 생성된 초안, 모델 버전, `review_confirmed` 값을 이력으로 기록(PRD §10.2)
- 코딩테스트 필요 여부 체크박스 값은 게시될 공고의 "코딩테스트 포함" 체크박스 기본값으로 그대로 반영(PRD §10.2)
- 편집 후 재저장 시 `review_confirmed`를 다시 false로 되돌릴지 여부는 운영 중 결정이 필요한 세부사항으로 남겨둔다

## B5. 지원자 목록

**1. 설계 대상 화면**: 공고별 지원자 리스트. PRD §5.2, Mermaid 03.

**2. 화면의 목적**: 공고에 지원한 지원자를 단계별로 필터링해 조회하고 상세로 진입한다.

**3. 주요 UI 구성 요소**
- 상단: 공고 선택 드롭다운(또는 B2에서 진입 시 고정 표시)
- 필터바: 진행 단계(서류/면접중/면접완료/코딩테스트중/완료/평가대기/결정완료)
- 메인 테이블: 지원자명, 지원일, 현재 단계 뱃지, AI 평가 요약 점수(관리자만 보이는 컬럼), 결정 상태, 행 우측 "상세보기" 버튼

**4. 사용자 동선 및 상호작용**
- "상세보기" → B6

**5. 반응형 및 접근성**
- 모바일: 테이블을 카드로 전환

**6. 프론트엔드 구현 시 참고사항**
- `GET /admin/applications?job_id=...`. AI 평가 점수 컬럼은 관리자 권한에서만 응답에 포함되어야 한다(PRD §7.2)

## B6. 지원자 상세

**1. 설계 대상 화면**: 이력서/면접 답변/코딩테스트 결과/AI 평가 전체를 열람하는 화면. 관리자 전용. PRD §5.2, §6.5, Mermaid 03/06/11.

**2. 화면의 목적**: 관리자가 지원자의 모든 산출물과 AI 평가를 검토해 최종 결정을 준비한다.

**3. 주요 UI 구성 요소**
- 상단 바: 지원자명/연락처/지원 공고/현재 상태
- 상단 탭: [이력서] [면접 답변] [코딩테스트 결과] [AI 평가 종합]
  - 이력서 탭: 표준화된 이력서 뷰 + 원본 PDF 링크
  - 면접 답변 탭: 질문별 리스트(질문 텍스트, 답변 전사, 음성 재생 버튼, 꼬리질문은 들여쓰기로 구분), 답변별 루브릭 점수(논리성/전달력/전문성/관련성) 소표시
  - 코딩테스트 결과 탭: 최종 코드(읽기 전용 에디터), 공개/비공개 테스트 결과, LLM 채팅 로그(허용/보완/반려 상태 뱃지 포함), 반려 이력과 감점 후보
  - AI 평가 종합 탭: 항목별 점수, 근거 인용, 신뢰도/검토 필요 뱃지, 감점 후보 확정/조정 입력, 관리자 메모 textarea
- 하단 고정 바: "최종 채용 결정" primary 버튼 → B7

**4. 사용자 동선 및 상호작용**
- 탭 전환 → 메모 작성/저장 → 감점 후보 검토(제안값 확인 후 확정/조정) → 저장 → "최종 채용 결정" 클릭

**5. 반응형 및 접근성**
- 데스크톱 전제. 탭 구조로 정보 과부하를 줄임

**6. 프론트엔드 구현 시 참고사항**
- `GET /admin/evaluations/{id}`, `POST /admin/penalty-reviews/{id}`
- **(v1.2 변경)** 이 화면은 면접·코딩테스트의 **모든** 세부 점수·근거·신뢰도/검토 필요 표시를 노출하는 유일한 화면이다. 지원자 화면(A11)에는 **면접 점수/AI 피드백 요약까지는 노출되지만, 코딩테스트 세부 평가와 평가 근거 원문·신뢰도 표시는 노출하지 않는다**(PRD §7.2). 즉 "관리자 전용"의 범위가 v1.1의 "평가 전체"에서 v1.2의 "면접 세부 근거 + 코딩테스트 세부 평가 전체"로 좁아졌으므로, 관리자용 API 응답 범위와 지원자용 API 응답 범위를 분리 설계해야 한다

## B7. 최종 채용 결정

**1. 설계 대상 화면**: 합격/불합격/보류 결정 및 통지. PRD §6.5, Mermaid 06.

**2. 화면의 목적**: AI가 아닌 관리자가 최종 결정을 내리고 이력을 남긴다.

**3. 주요 UI 구성 요소**
- 지원자명/공고명 표시
- 결정 선택: 합격/불합격/보류 3개의 큰 선택 버튼(라디오형)
- 결정 사유/메모 textarea(선택)
- 통지 미리보기(선택한 결과에 따른 메일 템플릿 미리보기)
- 하단 좌측 "취소", 우측 "결정 확정 및 통지 발송" primary 버튼

**4. 사용자 동선 및 상호작용**
- 결정 선택 → 메모 입력 → 확정 → 통지 발송(비동기) → 성공 토스트 → B6으로 복귀(상태 갱신 반영)

**5. 반응형 및 접근성**
- 3개 선택 버튼은 색상 구분과 함께 텍스트 라벨을 명확히 유지(합격=긍정색, 불합격=경고색, 보류=중립색 + 텍스트)

**6. 프론트엔드 구현 시 참고사항**
- `POST /admin/applications/{id}/decisions`, 결정·발송 이력은 append-only로 기록(PRD §7.3)

## B8. 질문 설정

**1. 설계 대상 화면**: 면접 질문 구성(유형별 문항 수, 질문은행/직접입력, 꼬리질문 상한, 제한시간). PRD §6.3, §6.6, Mermaid 03/05.

**2. 화면의 목적**: 공고별로 면접 질문 구성을 설정한다. 기본값은 인성2/자소서2/기업2/직무4(총10) + 꼬리질문 최대4이며 관리자가 조정 가능하다(PRD §6.3).

**3. 주요 UI 구성 요소**
- 상단: 공고 선택
- 유형별 섹션(인성/자소서관련/기업관련/직무관련) 각각: "문항 수" 숫자 입력(기본값 2/2/2/4), 섹션 내 질문 리스트, "+ 질문 추가"(질문은행 검색 모달 또는 "직접 입력" 토글)
- 하단 공통 설정: "꼬리질문 최대 개수"(기본 4) 입력, "문항별 제한시간"(초) 입력
- 상단 우측 "저장" primary 버튼

**4. 사용자 동선 및 상호작용**
- 섹션별 질문 추가/삭제 → 구성 완료 → 저장
- 저장 시 안내: "저장 내용은 이후 신규 응시자에게 적용되며, 이미 진행 중인 면접에는 영향을 주지 않습니다"(PRD §6.3 스냅샷 고정 원칙)

**5. 반응형 및 접근성**
- 데스크톱 전제

**6. 프론트엔드 구현 시 참고사항**
- `template_question_slots` 연계(기술아키텍처 §9). 실제 출제 질문은 변경 불가 스냅샷으로 별도 저장(PRD §6.3)

## B9. 평가 가중치 설정

**1. 설계 대상 화면**: 공고 단위 면접/코딩테스트 평가 항목 가중치 설정. PRD §6.5, §6.6.

**2. 화면의 목적**: 면접 루브릭(논리성/전달력/전문성/관련성)과 코딩테스트 항목(정확성/코드품질/검증·디버깅/프롬프트·AI활용판단/설명·근거)의 가중치를 공고별로 설정한다.

**3. 주요 UI 구성 요소**
- 상단: 공고 선택
- 면접 루브릭 4항목: 각각 슬라이더 + 숫자 입력, 합계 100% 실시간 검증 표시
- 코딩테스트 5항목(기본값 40/20/20/15/5): 동일한 슬라이더 + 숫자 입력 구성
- 하단 "저장" 버튼(합계가 100이 아니면 비활성 + 에러 메시지)

**4. 사용자 동선 및 상호작용**
- 값 조정 → 합계 검증 → 저장 → 안내: "이 가중치는 새 버전으로 저장되며, 기존 진행 중 평가에는 적용되지 않습니다"(버전 고정 원칙, PRD §6.5)

**5. 반응형 및 접근성**
- 슬라이더는 숫자 입력으로도 동일하게 조작 가능해야 한다(키보드 접근성)

**6. 프론트엔드 구현 시 참고사항**
- `rubric_weights` 버전 관리(기술아키텍처 §9). 이 가중치로 산출된 세부 점수는 B6/B9에서는 전체 노출되지만 A11(지원자)에는 면접 총점/피드백 수준까지만, 코딩테스트는 정상/비정상 여부까지만 반영되어야 한다(공개 범위는 API 레이어에서 분리)

## B10. 캘린더 및 일정 관리

**1. 설계 대상 화면**: 면접/코딩테스트 일정 조회·추가·수정, 통보 메일 발송 이력. PRD §6.6, §6.7, Mermaid 07.

**2. 화면의 목적**: 일정을 관리하고 알림 발송 상태를 확인한다.

**3. 주요 UI 구성 요소**
- 좌측(약 70%) 월간 캘린더
- 우측 패널: 선택 날짜의 일정 리스트, 상단 "+ 일정 추가" 버튼
- 하단 또는 별도 탭 "발송 이력" 테이블: 수신자, 유형, 발송 상태, 재시도 여부

**4. 사용자 동선 및 상호작용**
- 날짜 클릭 → 우측 패널에 해당 일정 표시
- "+ 일정 추가" → 모달(지원자 선택/유형/시간) → 저장 → 수락·조율 링크를 포함한 통보 메일 발송 트리거(PRD §6.7)

**5. 반응형 및 접근성**
- 모바일: 캘린더를 리스트형 일정 뷰로 전환 제안

**6. 프론트엔드 구현 시 참고사항**
- `notifications`/`email_events` 테이블 연계, 발송 실패 재시도·중복 방지는 백엔드 책임(PRD §6.7)

## B11. 직무별 통계

**1. 설계 대상 화면**: 직무별 지원/합격률/평가 추이 통계 조회. PRD §6.6, Mermaid 03.

**2. 화면의 목적**: 직무별 채용 성과와 AI 평가 활용도를 파악한다.

**3. 주요 UI 구성 요소**
- 상단: 직무 선택 드롭다운(전체 포함), 기간 필터
- 메인: 지원자 수 추이 라인차트, 단계별 전환율 퍼널차트, 평균 점수 바차트(그리드 배치)
- 하단 상세 테이블 + 우측 상단 "CSV 내보내기" 버튼

**4. 사용자 동선 및 상호작용**
- 필터 변경 → 차트/테이블 갱신 → CSV 내보내기

**5. 반응형 및 접근성**
- 차트는 데이터 테이블로도 동일 정보를 제공해 스크린리더 사용자를 배려

**6. 프론트엔드 구현 시 참고사항**
- 집계는 배치 처리로 충분하며 실시간성은 필수가 아님

## 제안 사항 처리 결과

v1.0에서 제안했던 3건에 대한 사용자 결정 결과(v1.1 기록 유지).

1. **"나중에 하기"(면접완료 후 코딩테스트 지연) — 반려.** 실제 평가로 취급되는 가상면접의 특성상 지연 옵션은 부적절하다는 판단. 대신 네트워크 중단에 대한 "이어서 진행"(A11/A7/A9)은 유지하고, 의도적 화면 이탈에는 강제 종료(A7/A8, 재개 불가)를 적용했다.
2. **장애인 대상 대체 응시 경로 — 보류.** 상세 설계는 이번 범위에서 제외하고, "향후 버전에서 장애인 대상 별도 구분 시험 트랙을 검토할 수 있다"는 각주만 A6에 남겼다.
3. **공고 자동 생성 "검토 완료" 수동 표시 — 반영.** B4의 "검토하기 → 검토완료" 토글(`review_confirmed`)로 통합 구현했다.
